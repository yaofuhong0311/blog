> 这是「Agent 工程」系列的第一篇。[沙箱系列](/posts/sandbox-deep-dive/)回答的是"该选哪个引擎"，这个系列回答的是"该怎么设计 agent 服务"——两者平级、不重叠。第一篇从最底层的机制开始：loop 内部到底在做什么。

## 一、地基：模型每一轮都在重发完整历史

模型侧不保存任何会话状态。所谓"它记得前面说过什么"，完全来自调用方每次把整段对话重新发送一遍——第 N 轮请求携带的是前 N−1 轮的全部消息加上本轮新增内容。**模型本身是一次性的无记忆函数调用。**

这一条是后面所有话题的地基。既然"会话状态"物理上就是那个只增不减的 messages 数组，那么：checkpoint 要持久化的是它，上下文窗口被撑爆的是它，压缩要处理的是它，服务端化要争夺所有权的还是它。**四个看似独立的话题指向同一个对象。**

## 二、循环不是风格选择，是结构性约束

模型无法执行任何工具，它能做的只是输出一个结构化的调用请求，随后**本次响应即结束**。真正持有执行能力的是调用方，因此控制权必须交回；而要把执行结果送回模型并让它继续，只能发起新的请求。

```text
一次 API 请求 = 模型的一个回合
```

推进 N 步就需要 N 次请求。用 `while` 而不是定长的 `for`，是因为 N 由任务复杂度和模型的临场判断决定，写代码时无从得知——同一份代码，"1+1 等于几"是 0 次工具调用，"找出所有调用方并改掉"可能是十几次。

```python
messages = [{"role": "user", "content": user_input}]

while True:
    response = client.messages.create(model=..., tools=tools, messages=messages)
    if response.stop_reason == "end_turn":
        break
    # 模型的整条回复原样入历史（含 tool_use 块）
    messages.append({"role": "assistant", "content": response.content})
    results = []
    for block in response.content:
        if block.type == "tool_use":
            output = execute(block.name, block.input)   # 唯一真正"动手"的地方
            results.append({"type": "tool_result",
                            "tool_use_id": block.id,
                            "content": output})
    messages.append({"role": "user", "content": results})
```

顺带纠正一个因果方向：**ReAct 是对这个结构的命名，不是它的成因。** 因果链是"模型只能提议、不能执行 → 一次请求只推进一步 → 必然形成循环"，而这个循环恰好就是 ReAct 所描述的对象。不是"为了实现 ReAct 而设计了循环"。

## 三、tool_use 与 tool_result：两条不能省的规则

请求里的 `tools` 只是一份说明书（名字、描述、参数结构），声明"你可以要求调用什么、参数长什么样"；**函数本身并没有交给模型，模型也无从调用**。

模型返回的内容是一个**内容块列表**，工具调用块与文本块并列——同一条回复中可以既有自然语言、又有工具调用。结果以 `tool_result` 块回送，**角色是 `user`**（不是独立通道，就是普通消息），靠 `tool_use_id` 与发起的调用配对。

两条规则违反了就会出问题，而且症状都不直观：

- **并行调用必须合并回送。** 模型可以在一条回复里发出多个调用块，此时所有结果必须放进**同一条消息**一次性返回。拆成多条发送会让模型后续不再发起并行调用。
- **工具失败也必须回送。** 执行报错时要返回带错误标记的结果，不能省略不回——模型在等待那个 id 的结果，缺失会让对话结构断裂。这是模型无状态的直接后果：**它不知道调用方那边发生了什么，一切必须显式告知。**

## 四、stop_reason：一个字段，三方成因

`stop_reason` 是服务端在生成结束时填写的诊断标签，取值来自固定枚举。**模型不会"选择"返回某个字符串**，它只负责产出内容，服务端观察其停止方式后贴标签。同一个字段背后是性质完全不同的几类原因：

| 取值 | 由谁导致 | 含义 |
|-|-|-|
| `end_turn` | 模型 | 输出了表示回合结束的标记 |
| `tool_use` | 模型 | 发出工具调用，等待执行结果 |
| `max_tokens` | **调用方自己** | 撞到调用方设置的输出上限，被强行截断 |
| `stop_sequence` | **调用方自己** | 命中调用方提供的停止序列 |
| `refusal` | 服务端 | 安全分类器判定不应作答 |
| `pause_turn` | 服务端 | 服务端工具的内部循环到达迭代上限，需原样再发一次续跑 |

**只判断 `end_turn` 的循环是一个会无限消耗额度的缺陷。** 当停止原因是截断或拒答时：条件不成立所以不跳出；随后到内容里检索工具调用块很可能一无所获（输出被截断或被拦截）；于是向历史追加一条**空消息**并回到循环顶部，极可能再次被截断，形成空转。**退出条件必须覆盖全部非工具调用的停止原因**，而暂停类的原因则需要原样重发以续跑。

## 五、上下文窗口：压缩不会自动发生

messages 只增不减，必然撞上上下文窗口上限。撞法有两种，而且第一种绕过了 `stop_reason` 的全部处理逻辑：

- **请求进门即被拒**——累积历史已超出窗口，本次请求在发送时就报错。这是**异常而不是停止原因**，循环直接崩在调用那一行。
- **生成中撞上**——返回一个专门的停止原因。它与输出上限是两回事：后者是调用方设置的**输出**上限，前者是**整个上下文窗口**耗尽。

平台提供的几条应对路径——服务端压缩、清除老的工具结果、自行截断或摘要——**全部需要显式开启**。

**这类"选择性开启"的功能，"未生效"是静默的正常状态。** 不传参数就不会压缩，接口不会报错也不会提示，只会在某次请求时直接失败——这正是它最容易被遗漏的原因。另外，启用压缩之后必须把响应内容**整体**追加回历史，只抽取其中的文本会丢失压缩块，导致下一轮无从得知此前压缩过什么。

这一条直接划出了一条服务边界：**自建 loop 意味着上下文管理归自己实现，而且不实现就是必然会炸的缺陷，不是可选优化**；托管型的 loop 则把压缩内置成了自动行为。

## 六、模型与 harness 的边界

"agent"这个词在日常使用中同时指代两样东西，混用会导致一连串错误推论。回看上面那段骨架，边界可以直接读出来：

```python
while True:                                      # ← harness
    response = client.messages.create(...)       # ← 模型（仅此一行）
    if response.stop_reason == "end_turn":       # ← harness
        break
    messages.append({"role": "assistant", ...})  # ← harness
    output = execute(block.name, block.input)    # ← harness
    messages.append({"role": "user", ...})       # ← harness
    persist(messages)                            # ← harness
```

**harness 不是叠加在 agent 之上的一层，harness 就是 agent 的本体**，模型是它内部调用的一个无状态函数：给定一段历史，返回"下一步想做什么"。所谓 agent，指的是二者合起来的整个程序。

![模型与 harness 的边界](/images/posts/agent-loop-boundary.svg)

由此得到一条**可以当判据用的通用原则：模型只能看到本次请求中塞给它的内容。任何需要跨请求、跨线程才能做到的事，必然在 harness。**

| 能力 | 需要什么 | 归属 |
|-|-|-|
| 决定下一步调用什么工具 | 仅需当前这段历史 | **模型** |
| 记住上一轮说过什么 | 跨请求 | harness（重发历史 + checkpoint） |
| 知晓子线程是否仍在运行 | 跨线程 | **harness** |
| 打断时连带停止子线程 | 跨线程 + 跨时间 | **harness** |
| 判定整个会话是否仍在运行 | 聚合多条线程 | **harness** |

所以"让模型监控子 agent 是否还在运行"这类想法在模型层面**无从谈起**——不是没授予它这个能力，而是**它所需的信息根本不在模型的输入之内**。这个判据后面会反复用到。

## 七、推论：概念本身由 harness 构造

模型的世界完全由 `tools` 中声明的内容构成——**"让模型知道存在某项能力"，其物理实现就是往 tools 数组里加一项，没有其它机制。** 模型不知道"读文件"是什么，只知道有个叫 `read_file` 的东西可用；其背后是本地文件操作、远程对象存储还是发往沙箱的请求，它全然不知也无需知道。

这解释了工具描述的分量：**它是模型理解一项自己从未见过的能力的唯一依据。** 同一个工具，描述写成"派生一个子任务"，和写成"当任务可拆为多个互相独立的部分时用它并行派发；单个文件的读写不要用"，行为差别很大。

但要补一句：模型并非白板，它在训练中见过大量 agent 系统，所以即便描述写得很薄，也会有大致合理的先验行为。**不应该依赖这个先验**——契约是你声明的那份，而你的实际实现未必与它的先验一致。
