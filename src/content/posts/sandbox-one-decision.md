> 本文是「沙箱底层机制」系列第 11 篇，也是全系列的收束。从[第一篇](/posts/sandbox-deep-dive/)的选型总览开始，中间讲了缺页、逃逸、编排、几个例外，又补了资源、存储、镜像、网络、调度与可观测。这一篇不引入任何新机制，只做一件事：**把前面所有内容收敛成少数几个可迁移的判断**。

十几个话题，表面上互不相干。但拆到底会发现，反复出现的其实只有**少数几个套路**——认出这几个套路，才是把零散知识变成判断力的关键，而不是记住十几个独立事实。

## 套路一：隔离到底隔的是什么

这条线串起隔离强度、整章威胁模型和 eBPF 的安全策略，是一条从"没有边界"到"硬件边界"的阶梯：

- **系统调用本身没有边界**——默认直达内核，谁都能走。
- **权限位与命名空间**是这条路上的**软件层限制**，本质是配置，所以能被错误放开——对应[配置性逃逸](/posts/sandbox-escape/)。
- **gVisor 的拦截层**在这条路上插入一个用户态实现的假内核，逃逸变成了要先打穿这个假内核。
- **microVM 的硬件地址翻译**是硬件级边界，架在 guest 内核之上——**guest 内核整个沦陷都出不去**。它做的是"guest 物理地址到宿主机真实物理地址"这第二层翻译，而且只有宿主机与 VMM 有权限写这张表，guest 没有任何软件手段能绕过。
- **内核漏洞**直接打共享内核本身的代码，**绕过以上所有层**——因为前面几层管的都是"进程能不能碰内核"，而漏洞本身就长在内核代码里，跟权限、跟命名空间都无关。
- **eBPF 验证器**是完全不同的第三条策略——目标不是隔离恶意代码，而是让工具代码安全地摸到内核内部，所以用的是"先证明安全再完全信任"，跟前面"先圈住再限制"的方向正好相反。

## 套路二：共享同一块物理资源，各自挂一个地址标签

同一个手法在三个完全不同的层各出现一次：

| 场景 | 共享的是什么，各自怎么映射 |
|-|-|
| fork 与写时复制 | 父子进程共享同一块物理内存页，各自页表指一份映射；首次写触发缺页、复制新页、更新写入方的页表项 |
| DAX | guest 和宿主机共享宿主机的页缓存，各自地址空间映射进来，省掉跨通道的数据拷贝 |
| eBPF 共享缓冲区 | 内核态和用户态共享一块内存，探针写入事件、用户态程序直接读取，无需拷贝 |

三个场景（进程之间、guest 与宿主机之间、内核态与用户态之间）完全不同，但都在解决同一个问题——**避免复制数据**。这不是巧合，是系统设计里"省拷贝"这个目标的标准解法。

## 套路三：创建时钉死还是运行时可改，决定了什么能热更新

权限位和命名空间在进程创建那一刻钉死，操作系统没有提供运行时动态增减的接口；而 cgroup 的限制运行时可写，内核立刻按新值生效。

这条分界线直接解释了一件事：**K8s 的 Pod 规格为什么大多数字段改不了、必须重建**，而原地扩缩容为什么能成为例外——因为它对接的底层机制本来就支持"活改"。**不是 K8s 特别照顾资源字段，是底层内核能力先天决定了谁能被暴露成"可热更新"。**

[存储那一篇](/posts/sandbox-storage-warmpool/)里"暖池与挂载无法同时成立"也是这条线上的例子：Pod 的卷列表属于创建时钉死的那部分，所以它是模型级的限制，不是实现没写好。

内存气球是这条线上的另一个例子：地址翻译表并非创建后完全钉死，宿主机可以通过气球机制让 guest 自己的内存分配器主动让出页（走正规内存管理通道，不是强行抢），再动态调整映射把真实内存收回。但如果索取过猛、guest 找不到足够可安全放弃的页，可能被迫在 guest 内部触发 OOM——这是气球机制真实存在的运维风险。

## 套路四：索引表加写时复制，在三个粒度各实现一次

| 层级 | 具体实现 |
|-|-|
| 内存页 | 页表：虚拟地址映射到物理页。共享只读源，首次写触发复制到新页、更新页表项 |
| 磁盘簇 | 簇表：虚拟磁盘簇映射到文件里的真实位置，或"未写过，去上一级找"。首次写触发分配新簇、复制合并原内容、更新簇表 |
| 整个文件 | 只读下层加可写上层：读取优先查上层，否则透传下层；首次写把整个文件复制到上层，下层原件从未被修改 |

三个粒度用的是同一个思想——**共享只读源 + 首次写触发复制到新位置 + 更新映射表指向新位置**，只是复制的对象大小不同：一页、一簇、一整个文件。

## 一个决策的七个投影

![七个角度是一个决策的七个投影](/images/posts/sandbox-one-decision.svg)

现在可以把结论说得更彻底一些：**七个选型角度不是七个独立事实。**

容器"共享内核"这**一个**选择，同时决定了它隔离弱、启动快（没有独立内核要引导）、资源限制是软的（靠 cgroup）、镜像分层是原生的、K8s 调度不挑节点、网络与可观测天然透明（进程就是宿主机上的普通进程）——但也因为共享内核，**暴露在内核漏洞面前**。

microVM 反过来，"独立内核"这一个选择，同时带来强隔离、慢启动（需要引导内核，靠快照与写时复制缓解）、硬资源分区、镜像要拼装、需要专用节点池、默认黑盒。

**选型选的不是七个维度，是"共享不共享内核"这一件事；七个角度只是把这一个决策的后果，从七个方向分别体现出来。** 理解了这一点，遇到第八个、第九个新维度时，第一反应应该是"这跟共享不共享内核这条根本分野有什么关系"，而不是从零开始积累新的独立事实。

## 两条主线

再往上抽一层，全部内容其实只在反复回答两个问题：

- **主线一（隔离与信任）**：这段代码、这块资源，能不能被安全地共享或者圈起来？
- **主线二（管理与编排）**：谁来确保这个东西长期维持在我想要的状态？

**主线一在七个粒度上被问了七次**，每次的答案不同：

| 粒度 | 同一个问题的答案 |
|-|-|
| 内存页 | 一个物理页被两个进程共享，靠写时复制加引用计数安全复制 |
| 磁盘簇 | overlay 与上一级共享磁盘数据，靠簇表加写时复制——同一个思想搬到磁盘 |
| 整个文件 | 多容器共享同一批镜像文件，靠文件级写时复制——又是同一个思想 |
| 一整个内核 | 容器（共享，弱）→ gVisor（拦截，中）→ microVM（硬件边界，强） |
| 内核内部一段代码 | 方向反过来——不是限制不可信代码，是让可信代码安全获得内核访问权限，靠"先证明再放行" |
| 字节码指令集本身 | 补全主阶梯缺的第四档——这个能力从指令集设计上就没存在过 |
| 一整块协处理器 | 反向验证了主阶梯为什么长这样——cgroup 能精细管 CPU 与内存，是因为内核本来就直接管这两样；GPU 不归内核管，同一套逻辑直接失灵 |

**主线二则是从"改一次"走向"持续对账"**：宿主机持续调整地址映射、内核在每次调度和分配时顺手查一下配额、controller 的对账循环贯穿资源整个生命周期、批量调度器持续判断"能不能一次性凑齐一组"——都是同一个模式。

**两条主线在哪里交叉？**[第四篇](/posts/sandbox-declarative-k8s/)里"超时前先快照再终止"那个设计就是交汇点：快照是主线一的产物（怎么安全捕获状态），controller 的持续监听触发是主线二的产物（怎么持续对账、及时补救）——缺任何一条都做不出这个方案。

遇到新问题时，可以先问"这属于隔离信任问题、管理编排问题，还是两者都要"，而不是从零摸索。

## 一条贯通的决策链

最后补一条**纵向的推导链**。前面归纳的是横向共性，而这条链从一个极普通的产品需求出发，每一步都只是接受上一步暴露出的约束，最终推出的却是整个系统的分层形状：

```text
产品需求：暖池要快，同时每个用户挂载自己的持久目录
  ↓ 暖池的前提是"提前起好、对谁都一样"，挂载的前提是"必须已知是谁"
需求内在冲突，且卷在创建时钉死、运行中无法热插
  ↓ 只能绕开，绕法有三条
①按需从对象存储拉取（不挂卷）②共享大盘加子目录（挂的是对谁都一样的东西）③放弃暖池
  ↓ 负载是 agent 生成的代码，不可信
②出局——子目录约定不是内核强制的边界，共享挂载点整棵树可达
  ↓ 需要真正的隔离边界
选择 microVM 强隔离
  ↓ microVM 需要宿主机的硬件虚拟化能力
必须圈出专用节点池，并用亲和性吸引加污点排斥双向约束调度
  ↓ 特权、宿主内核虚拟化、本地有状态盘、毫秒级专用调度均属 K8s 盲区
microVM 路线的引擎本就自带编排器、刻意不用 K8s
  ↓ 与其强行把引擎塞进 K8s，不如承认两者各有擅长
控制面与执行面解耦：无状态 facade 跑在现有 K8s 上，引擎集群在专用节点池自管，经 API 解耦
```

这条链上有三处判断值得单独记住，它们分别是三个话题的核心结论在具体决策中的落点：

- **暖池与挂载的冲突是模型级的，不是实现级的**——根因是卷在创建时钉死这个设计限制，因此不存在"实现得更好就能同时满足"的解法，三条绕法都是在别的维度上做妥协。
- **"可信负载"这个前提在 agent 场景下失效**——共享大盘方案的隔离由**应用层约定**而不是内核保证：共享挂载点整棵目录树在文件系统层面可达，最后一道防线只剩权限位，而多个沙箱同属一个用户身份时这道防线并不成立。它的性质属于配置性逃逸——访问该挂载点是被授权的合法操作，问题在于授权范围给成了整个盘而不是各自那一小块。
- **引擎的编排归属应当顺其设计而不是逆其设计**——microVM 所需的特权、宿主内核虚拟化、本地有状态盘与专用调度，恰恰是 K8s 的盲区，这也正是该路线的引擎自带编排器的原因；把它塞进 K8s 是逆着设计走，代价是持续增长的节点池与调度规则运维负担。

## 收尾

整个系列写到这里，最想留下的不是任何一条具体结论——引擎会换代，版本号会过时，今天的"不支持"明天可能就支持了（[第六篇](/posts/sandbox-resource-model/)里 GPU 那个结论就是个例子）。

真正耐用的是那套方法：**沿着底层机制往下追问，而不是对着参数表横向比较。** 追到底之后会发现，看似繁多的选型维度，往往都是少数几个根本决策的投影；而那几个根本决策，通常在你选定架构的第一天就已经做完了。
