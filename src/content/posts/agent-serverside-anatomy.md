> 本文是「Agent 工程」系列第 13 篇。前十二篇讲的是**该怎么设计**，这一篇换个方向：读一个真实开源框架的源码，看它**实际怎么做的**。对象是 [AgentScope](https://github.com/agentscope-ai/agentscope)——它自身是"框架层 + 服务层"两层结构，服务层是一个可直接运行的 loop 服务，不是示例代码。

先把结论放前面。判断一个 agent 系统是否真的面向服务端，有五条判据：

| # | 判据 |
|---|---|
| ① | 杀掉进程，会话是否丢失 |
| ② | 能否启动多副本、请求任意路由 |
| ③ | 同一会话的连续两轮，能否运行在不同机器上 |
| ④ | 是否存在"外部事件把已结束的会话重新拉起"的通道 |
| ⑤ | agent 停下等待外部输入时，**进程能否退出** |

**只满足 ①② 的系统非常常见**：把 checkpoint 存进数据库，但循环入口只接受 `reply(user_msg)`，缺 ④⑤。这类系统是**"可重启的单机 agent"，不是服务端 agent**。

好消息是 ④⑤ 都能单独补齐——补 ④ 是加一个队列和调度器，补 ⑤ 是把中断状态落库并让循环入口接受续跑事件，不需要推倒重来。下面逐条看它是怎么做的。

## 一、①②③：无状态副本的准确含义

它的 Agent 对象是**每次请求现场构造、请求结束即丢弃**的。构造时的七项参数——名称、系统提示、模型客户端、工具集、上下文配置、中间件、工作区——**没有一项由 Agent 自身产生**，全部来自数据库或现场装配。

这里有个措辞需要精确：**"无状态副本"指的是副本不持有不可替代的权威状态，而不是"每次请求都从零重建对象"**。事实上副本仍会缓存部分构件。区别在于——缓存丢了只是慢一点，权威状态丢了才是数据丢失。

支撑这一点的是**三类互相独立的持久化状态**：

| 状态 | 内容 | 存哪 | 隔离粒度 |
|---|---|---|---|
| 平台资源 | 用户、agent、会话、凭证、定时任务 | 关系库（每行带 `user_id`） | 用户 |
| 会话运行时 | 上下文、摘要、文件读缓存、权限上下文、任务进度 | 关系库的 JSON 列或 Redis | 会话 |
| 工作区文件 | skills、代码、依赖、卸载出去的数据 | **持久卷** | 工作区 |

**这三类必须被当作一个恢复单元。** 只恢复会话运行时而不恢复工作区，会出现"模型的上下文里记着写过某文件，但文件不存在"；反过来则是"文件在但模型没有相关记忆"。而它们的生命周期触发条件不同（副本重启 / Pod 回收 / 数据删除），所以必须分别持久化、共同恢复。

## 二、④：唤醒机制，以及一个消除竞争的做法

这是把"可重启"变成"服务端"的关键一环。它在消息总线上放了三个结构：

| 结构 | 类型 | 装什么 | 消费语义 |
|---|---|---|---|
| 每会话一个的 inbox | 列表 | 队友消息等**实际内容** | 该会话被唤醒后自行排空 |
| 全局唯一的唤醒队列 | 队列 | 运行触发条目 | **独占**：一条只被一个消费者取到 |
| 全局唯一的唤醒信号 | 发布订阅 | **空对象** | **广播**：所有副本都收到 |

**为什么需要队列和广播两套？**

```text
只用广播：所有副本都收到 → 都启动 run → 并发冲突
只用队列：无人通知，副本只能轮询 → 空转开销
两者配合：广播负责通知（可丢，丢了只影响时延）
          队列负责数据（不可丢，下次任何信号都会把积压一并排空）
```

**"可丢的通知 + 不可丢的数据"** ——这个组合后面还会再出现。

写入顺序也不能颠倒：**先入队再发信号**。反过来的话，信号到达时数据还没进队列，那次排空就是空的。

### 结构性消除竞争，而不是加锁

更值得学的是并发启动那个问题的解法。全系统**只有一处**调用"启动会话运行"——一个每进程一个的唤醒调度器，所有触发都经过这个串行消费者。

源码注释用的措辞是 **"structurally impossible"**，而不是"概率降低"：**竞争路径不存在，所以不需要为它加锁。**

而"会话是否在运行"的判定依据是 **Redis 分布式锁，不是本地任务表**——本地表对其它副本不可见。锁的实现是标准做法但细节到位：随机 token + 原子占用 + 心跳续期 + 释放时校验 token（**绝不删掉一个 value 不是自己的键**，否则会误释放别人刚拿到的锁）。租约默认十分钟、每五分钟续期，所以持有者进程崩溃后最多十分钟锁自动释放，其它副本接管——**这是滚动升级和故障接管能够成立的机制基础**。

### 同一个事实，在两种触发下含义相反

调度器取到条目后要按"触发类型 × 会话是否在运行"四种组合决策，其中有一处很容易写错：

| 触发类型 | 会话在运行 | 会话空闲 |
|---|---|---|
| `wake`（唤醒空闲会话） | **跳过**——存活的 run 会自行排空 inbox | 启动 |
| `resume`（把结果喂给一个停着的 run） | **退避后重新入队**——那个 run 正等着这个结果 | 启动并传入 |

**"会话正在运行"这个事实，在 `wake` 下意味着"已经有执行体会处理"，在 `resume` 下意味着"那个执行体正停在等这个结果的位置、还没释放锁"。** 弄反的后果：对 `resume` 采用跳过策略会让会话永久停滞，对 `wake` 采用重试策略会重复启动。

## 三、⑤：为什么恢复时必须判断中断状态

这条是我认为整篇最值得记的。

直接读出状态、重新发起一次模型请求是**不行的**，因为**上下文可能处于不合法状态**：

```text
[..., assistant: 文本 + tool_use(id=abc)]
                        ↑
              这个 tool_use 没有配对的 tool_result
              直接发请求会被 API 拒绝
```

这正是[第三篇](/posts/agent-checkpoint-chain/)讲过的**配对不变量**，在一个真实框架里的具体形态。所以它的循环入口接受**五种输入**：

| 输入 | 对应上一轮怎么结束的 |
|---|---|
| 用户消息 | 正常结束 |
| 空（`None`） | 正常结束，内容在 inbox 里 |
| **用户确认结果** | 停在"等待确认" |
| **外部执行结果** | 停在"等待外部返回" |
| **用户打断事件** | 任意位置 |

**后三种是服务端形态的必需品。** 命令行形态的 agent 只需要第一种——进程一直活着，中断状态就在内存里；服务端必须支持"进程已退出、状态已落库、外部事件到达后从中断点继续"。

**所以"循环入口能接受几种输入"可以直接当判据用。**

打断路径最能说明这个约束。用户打断时，代码**不能直接丢弃这一轮**，而必须给每个悬空的工具调用构造一个"已中断"的结果写回上下文，再结束。否则这个会话的上下文将**永久不合法**，此后任何一次模型请求都会失败。

**因此"判断中断状态"的目的不是决定要不要运行，而是确定需要怎么修补上下文使它合法。**

## 四、多 agent：子 agent 就是另一个会话

它的做法很干净：**子 agent 不是被调用的服务，而是同一个服务内的另一个 session。** 创建时做四件事——建 agent 记录、建独立 session（**工作区继承自 leader**）、写入团队名册、把初始任务投进 inbox 并触发唤醒。**全程没有 HTTP 调用。**

真正关键的是协作时序：

```text
t1  leader 派发任务
t2  worker 开始执行
t3  ★ leader 本轮结束，锁释放，进入空闲
      —— 此时该会话在任何进程中都不存在执行体
    ...worker 执行数分钟...
t4  worker 上报
t5  内容进入 leader 的 inbox
t6  唤醒队列收到触发，调度器启动新的 run
t7  中间件在推理前把内容注入上下文
t8  leader 读到上报，继续
```

**t3 是关键：leader 并不是在"等待"，它的执行体已经结束了。**

在 worker 跑的那几分钟里，leader 会话不占用任何进程、线程或协程。**因此不存在可供本地监控的信号**——这正是必须依赖持久队列而不是线程状态的原因，也是[第一篇](/posts/agent-loop-harness/)那条判据（跨请求跨线程的事必然在 harness）的又一次印证。

反过来看轮询模型的代价：一个 leader 加五个 worker、worker 平均跑十分钟，leader 就要占一个执行体空转十分钟；一千个这样的任务就是一千个空转执行体，而且 leader 所在的副本不能重启。**"结束 + 唤醒"是无状态副本能够成立的前提。**

这套模型甚至体现在提示词里：leader 版本的工具说明写着"**不要反复调用来查看成员进度**——成员完成后会主动通知你，等着就行"；worker 版本写着"**完成任务后必须调用此工具上报**"。同一个工具类、同一份代码，**按角色装配两份不同的说明书**——用提示词而不是代码分支来约束行为差异。

## 五、几个可迁移的模式

读完之后，有几个反复出现的手法值得单独列出：

| 模式 | 出现在哪 |
|---|---|
| **给可变对象附加一个单调变化的值，把"是否被改过"变成一次比较** | 文件用修改时间做乐观并发；分布式锁用随机 token 防误释放 |
| **结构性消除竞争，而不是加锁** | 唯一的启动点，并发路径不存在 |
| **可丢的通知 + 不可丢的数据** | 广播信号可丢，持久队列不可丢 |
| **代码负责把错误表述清楚，模型负责决定恢复策略** | 文件冲突、工具失败、参数不合法——**全都没有重试代码** |
| **同一实现按角色装配不同说明书** | leader 与 worker 两份工具描述 |
| **用能力约束替代路径约束** | 沙箱内的网关只绑回环地址，放弃网络可达性，换来"只有 exec 权限才能调用" |

第四条特别值得说。文件编辑冲突时，代码只做两件事：比对时间戳、返回一条错误状态的工具结果。**剩下的全交给模型**——它读到错误、决定重新读取、依据新内容重新确定要改的位置、再改一次。

**而这中间没有任何重试代码**，因为循环本来就在继续，模型本来就会读取工具结果。传统程序需要显式写重试逻辑，这里不需要。

## 六、也得说缺口

一个还年轻的开源项目，把缺口讲清楚比只讲优点有用。以下都是从源码直接可查的事实：

- **凭证以明文落库。** 全仓检索加密相关的关键词零命中——负责序列化的那个函数会把被遮蔽的密钥字段**还原成明文**再存。补齐的切点其实很集中（两条存储路径都经过同一个函数），真正的工作量在主密钥怎么存。
- **凭证进了 Pod 就是明文**，模型只要能执行 bash 就能读到。这与"凭证由平台在出口处替换、沙箱内永不可见"的保险库方案方向相反。
- **隔离只到用户级。** 默认策略下**同一个 agent 的多个会话共用一个工作区**——同一个 Pod、同一个卷、同一个文件系统，读文件的工具里没有任何路径校验。路径级隔离的机制存在（权限规则支持路径匹配），但**没有提供默认规则**，因为规则是静态配置，而"哪个会话属于当前调用方"要在运行时才知道。
- **没有组织/租户层**，企业多租需要自己在上面套一层并改掉全部按属主过滤的查询。
- **状态是覆盖写的**，没有父指针、没有版本链——[第三篇](/posts/agent-checkpoint-chain/)讲的时间旅行与分叉，这里做不了。而且保存发生在一轮结束时，进程在一轮中间崩溃会退回上一个保存点。

最后一条正好和[第三篇](/posts/agent-checkpoint-chain/)的结论对照：**落盘粒度决定崩溃时最多丢多少**。它选择了整轮保存，代价是崩在中途会重做一遍——这是个明确的取舍，不是疏忽。

---

读一个真实框架的最大收获，不是学到某个具体实现，而是看到那些**只有在服务端形态下才会浮现的问题**：会话锁、唤醒队列、中断状态修补、多副本装配。这些在单机 agent 里一个都不存在。

而它们能被逐条对上前面十二篇的讨论，也说明那些讨论确实落在真问题上。
