> 本文是「Agent Sandbox 工程实践」系列第 3 篇。上一篇沿着[一次真实的创建链路](/posts/agent-sandbox-create-path/)，区分了创建操作、Sandbox 生命周期和三类时间约束；这一篇继续讨论创建链路进入生产环境后，平台如何判断服务是否达标，以及如何定位没有达标的原因。

当一个 Sandbox 最终进入 Agent Ready，控制面已经完成了队列消费、资源创建、Pod 调度、容器启动和执行服务检查等多个阶段。

如果平台只记录一个总创建耗时，它能够回答：

> 用户等待了多长时间？

但它无法继续回答：

- 时间消耗在排队、调度、拉取镜像还是健康检查？
- 创建变慢是容量不足、资源碎片还是启动逻辑异常？
- 某次失败属于平台不可用、无效请求还是用户程序退出？
- 多副本控制器是否可能对同一目标重复执行扩缩容？

因此，创建控制面的生产能力不能只由“请求是否成功”描述。它还需要执行权约束、状态正确性、阶段可观测性和面向用户的服务目标。

![Agent Sandbox 创建链路的阶段指标](/images/posts/agent-sandbox-stage-metrics.svg)

## 一、Leader Election 只约束执行权

Autoscaler 或后台控制器通常需要部署多个副本，以避免单个进程故障后失去扩缩容能力。但多个副本同时运行，也会产生新的问题：谁可以修改同一个目标容量？

Kubernetes 中常见的处理方式是让副本竞争一个带有效期的 `Lease`。租约通常包含：

- `holderIdentity`：当前持有者；
- `renewTime`：最近续租时间；
- `leaseDurationSeconds`：租约有效期；
- `resourceVersion`：并发更新的版本条件。

`resourceVersion` 使同一轮竞争中只有一个更新能够成功，租约到期后其他副本可以接管。这解决的是“当前谁有权执行控制动作”，但它不证明动作只会发生一次。

例如，旧 Leader 在网络异常期间可能无法续租，却仍在本地继续运行；新 Leader 获得租约后，也可能开始计算并执行扩容。如果扩容动作依赖“当前副本再增加 5 个”这样的相对命令，两边同时执行就可能放大目标值。

更稳妥的方式是让控制器围绕统一的期望状态工作：

```text
observed capacity = 12
desired capacity  = 16

控制动作：把目标容量收敛到 16
而不是：在当前基础上增加 4
```

因此，Leader Election、Reconcile 和幂等分别承担不同职责：

| 机制 | 回答的问题 | 不能替代什么 |
| --- | --- | --- |
| Leader Election | 当前谁有权执行 | 幂等、状态收敛 |
| Reconcile | 当前状态与期望状态有何差异 | 业务动作是否可安全重复 |
| 幂等 | 重试是否保持相同副作用结果 | Leader 故障接管 |

把三者合并成一个“高可用开关”，会掩盖控制面的真实故障边界。

## 二、状态机说明走到哪里，阶段指标说明时间花在哪里

创建状态可以告诉调用方当前处于 `QUEUED`、`CREATING`、`READY` 或 `FAILED`。这些状态对恢复和用户解释很重要，但它们未必具备足够的性能诊断精度。

例如，同样处于 `CREATING`，可能分别是在等待调度、拉取镜像、启动容器或等待 execd 健康。如果只保存状态名称，平台仍然无法解释延迟来源。

更完整的创建记录需要保留关键时间点：

```text
t0  请求进入队列
t1  Worker 领取请求
t2  BatchSandbox 创建完成
t3  Pod 完成调度
t4  容器开始运行
t5  execd health 成功
```

阶段耗时由相邻时间点计算：

```text
queue_wait       = t1 - t0
resource_create  = t2 - t1
schedule_wait    = t3 - t2
container_start  = t4 - t3
health_wait      = t5 - t4
ready_latency    = t5 - t0
```

这种拆分不只是为了增加指标数量。每一段延迟对应不同的责任边界：

| 阶段 | 延迟升高时优先检查 |
| --- | --- |
| 队列等待 | 背压、Worker 吞吐、平台容量 |
| 资源创建 | API Server、Controller 处理、写入冲突 |
| 调度等待 | 资源碎片、规格约束、GPU 可用性 |
| 容器启动 | 镜像仓库、节点缓存、卷挂载 |
| 健康检查 | entrypoint、依赖安装、execd 启动 |

状态机主要服务正确性和恢复，阶段指标主要服务定位和优化。两者应当关联，但不应相互替代。

## 三、当前实现已经记录什么

当前创建入口已经使用单调时钟记录从创建处理开始到 Agent Ready 的整体时长，并写入一个直方图：

```python
_launch_duration = meter.create_histogram(
    "frontis.sandbox.launch.duration",
    unit="ms",
    description="agent-ready 沙箱创建时长",
)
```

成功和失败都会记录持续时间，并使用低基数状态标签区分结果。对应测试也验证了失败样本能够进入直方图，并带有 `sandbox.status=error`。

这是有价值的端到端指标。它接近用户实际感受到的等待时间，可以用于计算 Ready 延迟分位数，也可以观察不同 Runtime 的整体变化。

但它仍是一个合并指标：OpenSandbox 内部的资源创建、Pod 调度、镜像准备、容器启动和健康检查都会被计入同一个数值。仅凭这一条曲线，无法确定延迟由哪一层产生。

因此，本文对现状的判断是：

- **源码事实**：已经存在 Agent Ready 整体创建耗时和成功/失败状态；
- **当前边界**：该指标没有拆分 OpenSandbox 与 Kubernetes 内部阶段；
- **工程建议**：保留整体指标，同时补充阶段时间点、状态原因和跨层关联标识。

新增阶段指标不是替换现有指标，而是为现有端到端结果提供解释能力。

## 四、Metric、SLI 与 SLO 不是同一个概念

这三个概念经常同时出现，但所处层次不同。

### 1. Metric：原始测量

Metric 是系统直接记录的数据，例如：

- 当前队列长度；
- 创建失败数量；
- `ready_latency` 直方图；
- Pod Pending 数量；
- execd health 失败数量。

Metric 可以非常接近实现细节，并不天然代表用户体验。

### 2. SLI：实际表现

SLI 是从服务使用者角度计算出的表现，例如：

- 有效请求的创建成功率；
- Sandbox Ready 延迟的 P50、P95 和 P99；
- Sandbox Ready 后的 exec 可达率；
- 非预期消失率。

“最近一小时有效 CPU Sandbox 的 P95 Ready 延迟为 42 秒”是一个 SLI 结果，而不是目标。

### 3. SLO：目标表现

SLO 为 SLI 设定可验证目标，例如：

> 在 30 天窗口内，99.5% 的有效 CPU Sandbox 创建请求成功，并且 95% 在目标时间内进入 Agent Ready。

具体数值必须来自真实业务、容量测试和成本约束，不能在没有测量依据时直接确定。CPU、GPU、大镜像和带持久卷的 Sandbox 也不应共享同一延迟目标。

压测同样不是 SLI 或 SLO。压测用于验证不同负载下的 SLI 是否仍达到 SLO，并估算平台容量边界。

## 五、失败分类决定 SLI 是否可信

如果分母和失败原因没有定义清楚，成功率会失去解释价值。

以下结果不应归入同一类：

| 场景 | 建议分类 |
| --- | --- |
| Sandbox 已 Ready，用户命令返回 exit 1 | 用户任务失败 |
| 命令尚未下发，execd 无法连接 | 平台执行面失败 |
| 请求不存在的 GPU 规格 | 无效请求或容量拒绝 |
| Pod 因节点资源不足持续 Pending | 平台容量不足 |
| 调用方主动取消创建 | 用户取消 |

如果把用户命令失败计入 Sandbox 可用性，平台 SLI 会被业务代码质量影响；如果把无法满足的规格请求全部排除，又可能掩盖容量规划问题。

因此，每个 SLI 都需要同时定义：

1. 哪些请求进入分母；
2. 哪些结果视为成功；
3. 主动取消、无效请求和容量拒绝如何处理；
4. 统计窗口与分位数计算方式；
5. 按哪些稳定维度拆分。

这些定义比仪表盘上的单个百分比更重要。

## 六、SLO 未达标不等于需要扩容

当 Ready 延迟超过目标时，直接增加节点是一种不充分的判断。

正确路径应先回到阶段指标：

```text
SLO 未达标
├─ queue_wait 升高
│  ├─ Worker 已饱和：增加消费能力
│  └─ 平台容量不足：扩容或引入 Warm Pool
├─ schedule_wait 升高
│  ├─ 资源碎片：调整规格或调度策略
│  └─ 特定资源缺口：补充对应节点池
├─ container_start 升高
│  ├─ 镜像过大：优化分层
│  └─ 缓存命中下降：调整预拉取策略
└─ health_wait 升高
   ├─ entrypoint 阻塞：修正启动逻辑
   └─ execd 异常：检查依赖和健康探针
```

只有当证据指向容量不足时，扩容才是对应措施。否则，扩容可能增加成本，却不改变镜像、启动脚本或健康检查造成的延迟。

## 七、如果由我完善当前控制面

基于现有实现，我会按以下顺序推进。

### 1. 保留端到端 Ready 指标

整体创建耗时最接近用户体验，应继续作为核心 SLI 数据源。阶段指标用于解释它，而不是替代它。

### 2. 在创建操作中保存阶段时间点

优先保存事件时间，而不是只在进程内计算临时耗时。这样即使 Worker 重启，创建操作仍能恢复，并可以重新计算阶段耗时。

时间点应来自对应状态的权威来源。例如 Pod 调度时间应根据 Pod Condition 或 Kubernetes Event 确认，而不是由上层请求返回时间近似代替。

### 3. 建立稳定的失败分类

错误码需要区分无效请求、容量拒绝、平台创建失败、健康检查失败、用户取消和超时。Metric 标签只保留 Runtime、规格类别、状态和错误类别等低基数维度；Sandbox ID、Session ID 等高基数信息进入 Trace 或日志。

### 4. 再定义分层 SLO

先积累真实分布，再按 CPU、GPU、镜像缓存条件和持久化需求定义不同目标。没有足够样本时，先发布 SLI，不提前承诺缺少依据的 SLO。

### 5. 控制器多副本化时补齐执行权边界

只有在 Autoscaler 或回收控制器需要多副本主动执行时，Leader Election 才成为必要机制。引入租约后，扩缩容仍必须围绕统一期望状态设计，并保留幂等和 Reconcile。

## 结语

一个可运营的 Sandbox 平台，需要同时回答四个问题：

1. 当前由谁执行控制动作；
2. 系统状态是否正在向期望状态收敛；
3. 时间具体消耗在哪个阶段；
4. 用户实际体验是否达到目标。

Leader Election、状态机、阶段指标和 SLI/SLO 分别回答这些问题。它们不是同一套机制的不同名称，也不能互相替代。

整体创建耗时仍然重要，因为它代表用户真正等待的结果。但只有把它与阶段时间点、失败分类和控制面状态关联起来，平台才具备解释异常、定位瓶颈和选择治理措施的能力。
