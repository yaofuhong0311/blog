> 本文是「Agent 工程」系列的最后一篇。前六篇的机制都假定 loop 正常推进，这一篇处理它不正常时的三类问题：模型原地打转、"完成"无法判定、以及各层失败该不该重试。三者共享同一个前提——**harness 不是旁观者，每一次工具调用都由它亲手执行，它始终在数据通路上**；而它的盲区自始至终只有一个：语义。

## 一、打转：定义是"消耗在增加、进展为零"

典型场景：模型跑测试失败 → 修改 → 再跑 → 又失败 → 改回去 → 再跑，来回十余轮毫无进展。

**注意这与[第一篇](/posts/agent-loop-harness/)那个空转缺陷不同**：那里是 harness 处理停止原因不全导致的，此处 harness 完全正常，每轮的停止原因都是合法的工具调用、结构也没问题，是模型自身在原地转。

**"重复"只是打转最便宜的代理信号，不是它的定义。** 真实的打转常常表现为"换个写法的同一个思路"——每轮的调用与参数都不同，精确匹配一个也抓不到；反向的误伤同样存在：同一条测试命令连跑五次、轮询构建状态，重复本身就是正常工作。**修正后的判别是：同样的动作是否得到同样的结果，且期间没有任何状态变化。** 测试跑五次而失败数逐次减少是进展；跑三次错误一字不差、中间的修改又被改回去，才是打转。

| 检测信号 | 成本 | 漏报 | 误报 |
|-|-|-|-|
| 精确重复（同调用 + 同结果） | 极低 | 高——换个写法即漏 | 低（需配合"中间无状态变化"） |
| 归一化的报错签名反复出现 | 低 | 中 | 低 |
| 状态无变化（文件系统、待办未动而额度在消耗） | 中 | 低 | 中——深度思考期也无动作 |
| 拿转录问一个独立模型"这段有无进展" | 高 | 低 | 有，且评判者自身也会错 |

所有检测都是以代理信号逼近，注定有漏有误——根因在于**判断"有无进展"需要一个目标度量，而 harness 通常没有**。

这里有个值得琢磨的悖论：按"每轮完整重发历史"的规则，模型明明"看得见"自己在重复，为什么不停？**因为"信息在上下文里"与"注意力落在其上"是两回事**（[上下文那篇](/posts/agent-context-engineering/)的稀释效应）：转到第 15 轮时上下文已堆满测试输出与差异，"我第 3 轮就试过这个"淹没其中——它看得见，但没在看。

**这正是检测必须由 harness 的确定性代码承担、而不能指望模型自觉的原因：代码不会分心。**

## 二、三层防线：检测 → 干预 → 止损

最大轮数是必须有的，但它属于**止损**而不是**发现**——上限对"打转"与"正常推进"一视同仁，只是一个数字到点：打转的会话会一直消耗到触顶，正常的复杂任务则被拦腰砍断。它解决"最坏能坏到哪"，不解决"何时出了问题"。完整的防线是三层，前两层比它便宜得多：

1. **检测**——确定性代码做跨轮比较。历史全在 harness 手里，这是普通的字符串比较与计数，不需要任何智能。
2. **干预**——先试**注入提醒**：往下一轮追加一条消息，明确指出"你已第 3 次执行同一命令并得到同样报错，请重新审视假设"。**很多打转靠这一句就解开**——模型不是没能力跳出，而是注意力没落在"我在重复"上，你替它把这个事实提到最显眼的位置。无效则**换环境**：从打转开始之前的 checkpoint [分叉重来](/posts/agent-checkpoint-chain/)，或者派一个干净上下文的子 agent 来看——它没有那十余轮的污染，常常很快就能定位问题。
3. **止损**——上限兜底；再不行就停下问人，把"卡在哪、试过什么"整理交给用户。**在无效轮次上省下的钱，比硬撑到上限有价值得多。**

干预的第一层之所以是"提醒"而不是直接终止，正因为检测必然有误报——**误报的代价只是多一句话，不是杀掉一个正常任务。**

## 三、"完成"判不了，是原理性缺口

打转检测依赖"有无进展"，而进展需要目标度量——问题就落在这里：**harness 判断不了"完成"，这不是实现不足，是原理性的。**

"完成"与"打转"是同一枚硬币的两面，都是语义判断、都需要理解任务目标；而 harness 手里只有结构信号（调用了什么、返回了什么、文件变没变）。它能看到模型发出结束标记，但那只是**模型宣称完成**，不是完成——**模型提前宣称"已完成"与原地打转，对 harness 而言是同一盲区的两个症状。**

按[第一篇](/posts/agent-loop-harness/)的判据走一遍即可确认这是死局：判断"完成"需要理解任务语义加一个目标定义。**前者 harness 没有，后者通常也没有；模型有前者，但它的自评不可信**——它已经被自己十余轮的历史说服了。

实际解法不是让 harness 变聪明，而是**把"完成"改造成可检验的**。三条路，可靠性递减：

| 路径 | 做法 | 适用 |
|-|-|-|
| **机器可检验的目标** | 把语义目标翻译成结构信号：修到测试通过 = 退出码为 0；改到能编译 = 编译成功；生成数据文件 = 文件存在且结构校验通过 | 任务自带验证器 |
| **独立评审** | 事先把"完成长什么样"写成可逐条打分的标准，交给**干净上下文**的评审者对产出打分 | 无天然验证器（例如写一份分析报告） |
| **交给人** | 承认判断不了，把"卡在哪、试过什么"整理后交给用户 | "完成"本就只存在于用户脑中 |

第一条路顺带解决了打转检测：有了目标度量，"进展"就有了定义——失败的测试数在减少即为进展，纹丝不动即为打转。**这也是编码类 agent 比开放式任务的 agent 可靠得多的真正原因：不是模型在代码上更聪明，而是代码任务天然自带验证器。**

第二条路有两个不可省的要点：评审者必须是**独立上下文**（执行任务的那一个自评不算数，理由同上下文防火墙）；标准必须**事先定义**（事后让评审者自由发挥，它同样没有依据）。

由此得到一条设计原则：**agent 的可靠性上限，取决于任务的"完成"能被多硬地检验。** 所以设计 agent 任务时最值钱的一步不是调提示词，而是**把目标改写成可检验的形式**——能写成测试就写成测试，写不成就写成评分标准，两者都写不出，就接受这个任务需要人在环里。**缺口不是被消灭的，是被逐级外包的。**

## 四、两个检查点：harness 一直在数据通路上

"判不了完成"看似意味着必须等 agent 停下来才能评判，其实不必——**每一次工具调用都由 harness 亲手执行**，因此"测试是否通过"这类信息，第一手就在它手里，它拿到的是结构化的退出码，无需等待、也无需理解任何语义。

**检查点 A：流中观察（agent 仍在运行时）。** 模型每次发起测试，harness 执行、取回退出码、包成结果回送——顺手就能记录该指标，于是进展曲线是免费得到的：

```text
第 3 轮   exit=1, 失败 12 个
第 7 轮   exit=1, 失败 5 个     ← 有进展，不要打扰
第 11 轮  exit=1, 失败 5 个
第 15 轮  exit=1, 失败 5 个     ← 三轮未动，这才是打转
第 18 轮  exit=0                ← 目标达成
```

**这解决了第一节那个"重复不等于打转"的难题**：判据不再是"命令是否相同"，而是"客观指标有没有动"。

**检查点 B：终局校验（agent 宣称完成之后）。** 模型宣称已完成 → **harness 自己再跑一次验证**，不采信其自述：通过则确为完成；未通过则把真实结果回送（"测试仍失败，输出如下……"），让 loop 继续。

**这是"完成"这件事上唯一可靠的机制：模型的结束标记只是一个提议，批准与否由 harness 拿客观证据说了算。** 同理，评审也不必等它结束——可以挂在终局（不合格则带着"哪几条未达标"打回继续，构成**外层循环**：执行 loop → 评分 → 不过则回炉，与内层的工具调用循环是两层），也可以每若干轮过程抽检（早发现早止损，代价是每次抽检都是一次额外的模型调用）。

## 五、重试：先分清失败的层级

"失败了要不要重新执行"没有统一答案——**取决于是哪一层挂了，三层的处理完全不同**：

| 层级 | 例子 | 处理 |
|-|-|-|
| **传输层** | 网络超时、限流、服务端错误 | **可重试**，退避即可——但前提见下 |
| **工具层** | 命令执行失败、文件不存在 | **不重试**——把错误当结果回送给模型，由它决定怎么办 |
| **任务层** | 打转、评审不通过 | 重试无意义，**必须换条件**（换环境、换方法、问人） |

**工具报错不是 harness 的异常，而是 agent 的输入**（回扣第一篇的"工具失败也必须回送"）。harness 自动重试"删除一个不存在的文件"，只会重试三次得到三次同样的错；而模型看到这个错，很可能立刻明白"这个文件我已经删过了"。**判断权在模型，不在 harness。**

**传输层重试的前提是幂等——超时不代表没执行。** 请求发出、下游收到并已执行、响应在回程超时，harness 若判定失败并重试，同一操作就被执行了两次。所以传输层重试要么针对天然可重复的操作（读），要么携带幂等键交由下游去重（与[重放](/posts/agent-checkpoint-chain/)时用的是同一手段）。**不幂等的操作盲目重试，比不重试更危险。**

## 六、收尾：翻译得越彻底，agent 越可靠

本篇的共同答案是：**harness 之所以能检测、能校验、能重试，不是因为它聪明，而是因为一切都从它手上过**——退出码、产物、请求有没有回来，全是结构信息，不需要理解任务。**它的盲区始终只有语义。**

所以设计上的功夫全花在同一件事上：**把语义目标翻译成它看得懂的结构信号**（退出码、结构校验、评分表）。翻译得越彻底，agent 越可靠。

整个系列七篇写下来，如果只留一条，我会留[第一篇](/posts/agent-loop-harness/)那个判据：**模型只能看到本次请求中塞给它的内容；任何需要跨请求、跨线程才能做到的事，必然在 harness。** 本系列后面六篇里的每一个结论——上下文该放什么、状态该由谁持有、监控归谁、完成由谁批准——都是它的直接推论。

系列到此完结。
