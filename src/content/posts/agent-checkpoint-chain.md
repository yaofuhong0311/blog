> 本文是「Agent 工程」系列第 3 篇。[第一篇](/posts/agent-loop-harness/)说过，会话状态物理上就是那个只增不减的 messages 数组。这一篇讨论它该由谁持有，以及持久化它的正确形态。

## 一、状态放在客户端，会同时失去四项能力

那份数组总需要有人持有。如果服务端不保存，就由客户端持有并在每次请求时上传完整历史，服务端退化成无状态中转。这种形态可以运行，但会同时失去四项能力——而这四项恰好就是"服务端化"的动机本身：

| 失去的能力 | 后果 |
|-|-|
| **checkpoint** | 历史存在客户端内存里，进程崩溃、页面关闭或网络中断即永久丢失，服务端连"这段对话进行到哪了"都无从得知 |
| **多端接入** | 状态绑定在发起端，换一个客户端无法接续同一段对话 |
| **审计** | 服务端只是过路中转，不留下执行过哪些工具、读写过哪些文件的记录，事后无从追溯 |
| **权限与信任边界** | 历史既然由客户端上传，就可以被客户端篡改（伪造助手消息、改写工具执行结果），服务端没有权威副本可供比对 |

服务端化的实质，是把 messages 及围绕它的 checkpoint、工具调用记录的**所有权**从客户端迁到服务端：客户端不再上传历史，只提交本轮输入与会话标识；服务端据此从自有存储取出权威历史、拼装、调用模型、执行工具，并把新状态写回。**客户端由"状态持有者"降级为纯展示层。**

## 二、一个物理事实：存储可以有版本，世界没有

agent 的状态实际分布在两个互不相干的地方，这是后面所有困难的来源：

| 状态 | 存放位置 | 可否回滚 |
|-|-|-|
| **对话状态** | checkpoint 存储 | 可以，能重放到任意一步 |
| **世界的副作用**（文件已改、邮件已发、数据库已写） | 外部世界 | **不可以** |

所以"恢复"天然是不完整的：可以把对话倒回某一步，但那之前已经发生的副作用撤不回来。**这不是实现缺陷，源于一个物理事实——存储可以有版本，世界没有。**

## 三、崩溃与打断：区别在于历史结构是否可控

loop 中可以停下的位置有五处：① 发请求前 ② 模型生成中 ③ 收到回复未执行工具 ④ 工具执行中 ⑤ 工具已完成但结果未记录。①②③ 处什么都还没发生，历史停在上一轮的完整状态；**④ 才是真正的问题所在**，而且问题有两层：副作用层（与崩溃相同，撤不回）与**结构层**（打断特有）。

**配对不变量：历史中每一个工具调用都必须有对应的结果。** 在 ④ 处就地停下存盘，最后一条将是悬空的调用，这份历史结构非法——下次恢复时把它发给模型会直接报错。**因此打断不能"就地停下存盘"，必须先给悬空的调用收尾。**

实际做法是两个机制配合：**打断是"请求停止"而不是"立即杀死"**，让执行跑到一个安全边界（当前工具执行完、结果记入历史）再停；确实停不下来时，**用一个合成的结果封口**，内容说明该调用被打断未完成并标记为错误。后者并不是在欺骗模型——恰恰因为模型无状态、不知道调用方发生了什么，**必须显式告知"这次没成"**，这是[第一篇](/posts/agent-loop-harness/)里"工具失败也必须回送"的一个特例。

|  | 副作用 | 历史结构 |
|-|-|-|
| **崩溃** | 撤不回 | **可能是坏的**（悬空调用），需要事后修复 |
| **打断** | 撤不回（相同） | **可以保证是好的**——尚有机会封口 |

判据是"**有没有欠模型一个交代**"：打断时若不存在悬空调用（①②③），模型对打断毫无感知，历史原样存盘即可；若存在（④⑤），就必须补上一条结果，两者的差别仅在这条结果是合成的（④，没有真实结果）还是真实的（⑤，结果已得只是尚未记录）。

由此得出一个实现约束：**打断处理器必须能查询"当前有哪些待完成的工具调用"，因此这个状态必须被显式维护为一等状态，不能只隐含在调用栈的局部变量里。**

## 四、送达不等于落盘

"agent 处理完了但客户端没收到"属于**送达失败**而不是状态丢失，可恢复。前提是顺序正确：

```text
正确：先落盘 → 再送达     最坏情况「存了但没送到」，客户端重读即可补上
错误：先送达 → 再落盘     两步之间崩溃 → 客户端收到了、服务端没存 → 双方状态不一致
```

规则是**宁可重复送达，不可丢失状态**——读操作重复无害，状态丢失不可逆。副作用是同一结果可能被送达两次（客户端超时重连），如果客户端收到结果后会触发下游动作，需要按消息 id 自行去重。

这里要纠正一个说法：**无状态的是模型，不是 agent。** 模型不保留任何会话状态；而 agent（loop 服务加存储）恰恰是持有状态的那一方——**这正是恢复得以可能的原因**。把两者混称会直接导致"agent 无状态所以恢复不了"的错误推论。

## 五、落盘的粒度：落点不是自由选择

一轮完整对话内部可能包含十余次循环迭代，**在哪些点落盘决定了崩溃时最多丢多少**。如果整轮结束才存一次，崩在中途会得到最糟的组合——**副作用已经发生，却没有任何记录证明它发生过**，恢复后会从头重做一遍（文件被改第二次）。每次迭代都落盘则最多丢一步，代价是写入频率。

**而落点其实不是自由选择，它由配对不变量决定：应该落在每个工具结果补齐之后。** 如果在"调用已追加、结果未追加"的中间态落盘，存下来的就是一份非法历史。由此得到一个有用的性质：**链上最后一个 checkpoint 必定可续跑**，无需额外判断它可不可用——落点规则已经保证了这一点。

## 六、内容：不止 messages

| 内容 | 为何必需 |
|-|-|
| messages 数组 | 对话主体 |
| 执行位置 | 停在哪一步；图框架下就是当前节点与下一条边 |
| messages 之外的累积状态 | 待办清单、已读文件表、长期记忆、计数器——不在对话里，但丢了行为会变 |
| 本次运行的绑定 | 版本、工作区、挂载的工具集。**最易遗漏**：如果恢复时工具集或配置与当初不一致，模型面对的世界与它当初推理的世界不符，行为将不可解释 |

**恢复的目标是还原当时的完整上下文，而不仅仅是当时说过什么。**

## 七、它是一条链，不是一个值

直觉上 checkpoint 像"存档"——一份，新的覆盖旧的。实际通常是一条链：每步存一个，各自带指向上一步的指针。保留全部历史而不是只留最新值，是为了两件只有链才能做到的事：

- **时间旅行**——回到任意一步查看当时的完整状态。只存最新值时，出了问题只能看到结局、看不到过程。
- **分叉**——从某一步拉出新线重跑而不破坏原线。**这不是改写历史，是从某点长出新分支。**

分叉并不抽象，它就是聊天界面里的**"编辑上一条消息"与"重新生成"**：

```text
提问 A → 回答 A' → 提问 B → 回答 B'
   │
   └─ 回头把「提问 A」编辑为「提问 A2」
          ↓
       回答 A2' → ...        （新分支）
```

关键在于**旧的那条并没有被删除**——界面上那个 `< 2/2 >` 切换箭头切的正是这两条分支。底层就是：在"提问 A"之前那个 checkpoint 上挂了一个新的子节点。同理还有重新生成（从模型回复前一步分叉重跑）、调试（从出错前一步分叉试改，原始故障记录仍在）、方案对比（同一起点跑两种做法并留存比较）。**如果 checkpoint 只存最新值，这些功能一个都做不了。**

顺带厘清它与"state"的关系：**内容是同一批东西，区别在形态。** 类比版本控制：state 是工作区（活的、随时在变），checkpoint 是一次提交（冻结、带编号、记录父节点）。提交里装的与工作区里的是同样的文件，二者不是二选一的关系。

```text
checkpoint = state 的一次持久化快照 + 它在链上的位置信息
```

它比 state 多的不是内容，而是三样元信息：**持久化**（进程死后仍在）、**身份**（可被寻址，"取会话 X 第 3 步"）、**不可变且有序**（固化后不再修改，串成链）。缺少这三样就只剩一个"当前值"：进程一死即失、无法回溯、无法分叉。

## 八、续跑与重放：必须是两条代码路径

两个常被混为一谈的操作：**续跑**从链的末端接着走，已经做过的事一件不重做；**重放**回到链中间某点重新往前跑，其后的步骤会再执行一遍。崩溃恢复用续跑；时间旅行、分叉、"重新生成"用重放。

**续跑安全，因为它不重跑；重放危险，因为它重跑而世界不会跟着倒回。** 从第 3 步重放时，如果第 4 步曾发出一封邮件，重放将再发一封——状态干净地回到了第 3 步，但那封邮件已经在对方收件箱里。这是重放的本质困难，不是实现缺陷。

**所以"崩溃恢复"与"重新生成"虽然同样依赖 checkpoint 链，却必须是两条不同的代码路径**：前者可以自动执行，后者通常需要人工确认。

三种常见的缓解手段：

- **重放走分叉而不是覆盖**——不解决副作用，但保住记录；覆盖之后连"曾经发过"都查不到。
- **区分纯步骤与有副作用的步骤**——重放读取无害，重放发信不行，后者跳过或停下问人。
- **幂等键**——调用时携带唯一 id，工具端记录已处理过的 id，重复请求直接返回上次结果。**把去重责任交给最了解自身副作用的一方。**
