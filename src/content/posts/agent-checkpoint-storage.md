## 一、核心是一张只追加的表

从存储层看，其结构相当朴素：

| 字段 | 作用 |
|-|-|
| `thread_id` | 所属会话，查询的主键维度 |
| `checkpoint_id` | 本步自身的 id |
| `parent_id` | 指向上一步——**链就是靠这一个字段串起来的**，分叉无需特殊支持：两行的父指针指向同一节点即成两条分支 |
| `state` | 序列化后的状态本体 |
| `metadata` | 步序、时间戳、触发来源 |

**写路径只 INSERT，从不 UPDATE。** 每步插入一行新记录，而不是覆盖既有行。只追加带来三项直接收益：**不可变**（历史不被改写，时间旅行才有意义）、**无并发更新竞争**（各插各行，不互相覆盖）、**原子性天然成立**（一次插入要么成功要么失败，不存在"写了一半"的行被读到）。最后一项让"写入必须原子"这件事由数据库事务免费提供，无需自己实现"先写临时文件再重命名"。

```sql
-- 续跑：取该会话最新一份
SELECT * FROM checkpoints WHERE thread_id = ? ORDER BY checkpoint_id DESC LIMIT 1;
-- 时间旅行：按 id 直接取
SELECT * FROM checkpoints WHERE checkpoint_id = ?;
-- 完整历史：自某点顺着父指针回溯
```

因为每行存的是全量快照，"跳到任意一步"就是一次索引查询。

## 二、中间节点为什么删不得

这是最反直觉的一条：**普通链表的节点是独立的值，checkpoint 节点是累积的值。**

设第 3 步是"读文件"。删掉第 3 步、把第 4 步的父指针改指向第 2 步之后，**第 4 步的状态里仍然装着读文件那对调用与结果**——指针声称"接在第 2 步之后"，内容却包含第 3 步的产物，二者不再自洽；模型读到这段历史，会看到一个凭空出现、无人发起的工具结果。

要真正删除，只能重算它的全部后代，而"重算"就是重放，重放就是重新执行，副作用问题随之回来。

与版本控制对照：删除中间提交就是变基，那边可行是因为它能**重新计算**后续提交；而 checkpoint 的"重新计算"等于**重新执行 agent**，代价完全不同。

由此：

- **删除**物理可行，但会断链——所有以它为父的后代将指向不存在的节点，该段的时间旅行随之失效。所以删除的实际粒度通常是**整条会话**；按过期时间裁剪时也应当**从最老的一端向前剪**，保持近期链完整可续跑，代价是无法回溯到更早。
- **插入**在语义上不成立——第 N 步的状态是"执行第 N−1 步到第 N 步"的产物，无法凭空构造中间态。**分叉才是被认可的那种"插入"**：为已有节点挂上新的子节点，链因此成树，原线不动。

## 三、全量快照的代价是平方级

**每步存全量快照意味着单条会话内的存储量是 O(n²) 而不是 O(n)。** 一个跑了 20 步的会话，第 1 步存 2 条消息、第 20 步存 40 条——早期消息在其后每一份快照中都被重复存储一次。长会话的 checkpoint 表体积会显著超过"这些对话文本本身"的大小。

那为什么还这么做？因为改存纯增量的代价不止于"慢一些"：

- **随机访问丧失**——要取第 N 步状态必须从头逐级叠加，常数时间退化为线性时间。
- **分叉更繁琐**——必须先走到分叉点还原状态。
- **故障不再隔离**——这是最具决定性的一条：增量模式下中间任一节点损坏或丢失，**其后全部无法重建**；全量快照模式下损坏一个节点只丢失该点，前后仍可用。**全量快照的冗余不是浪费，而是故障隔离**——每份快照都能独立自证，不依赖任何其它节点。

标准折中是混合方案，与视频编码同一思路：每隔若干步存一次全量（关键帧），其间存增量。

```text
关键帧            增量  增量  增量   关键帧            增量  增量
ckpt#1(全量)  →  Δ2 → Δ3 → Δ4 →  ckpt#5(全量)  →  Δ6 → Δ7
```

恢复最多回溯到最近的关键帧，故障影响也被限制在一个区间内。另一条路是**消息独立存储加引用**：checkpoint 内只存消息 id 列表，消息本体去重存在另一张表，兼顾空间与寻址，代价是实现复杂度。**空间、寻址速度、实现复杂度三者只能取二。**

## 四、并发：分叉从功能变成故障

```text
写入者 A 读到「最新是 ckpt#3」──┐
                              ├─→ 两者都插入父指针为 ckpt#3 的新节点
写入者 B 读到「最新是 ckpt#3」──┘
结果：ckpt#3 长出两个孩子，「当前状态」不再唯一
```

同一个机制，有意为之时是分叉功能，并发意外触发时就是数据故障。两种解法：**同一会话单写入者**，用锁或租约保证任一时刻只有一个执行者推进它；或**乐观并发**，在"会话加父指针"上加唯一约束，第二个插入直接冲突失败并重读重试。

**读路径同样受影响。** 用"排序取第一条"取最新，这个操作在并发下本身就不可靠——读到的"最新"下一刻可能已经不是了。真正的推进动作必须把**读与写置于同一个事务或同一个租约内**，不能分开执行。

## 五、子 agent：同库，不同链

先看派生的完整时序，注意**模型只出现在第一步**：

```text
① 模型输出 {"name": "spawn_subagent", "input": {"task": "..."}}
   ↑ 模型做的全部事情，仅此一步
──────────── 以下全部由 harness 完成 ────────────
② harness 收到该调用，识别出此工具的实现是「起一个新 loop」
③ 创建 thread_B（父会话指向 thread_A）
④ 在 thread_B 上跑一整套完整的 loop（自己的循环、工具、checkpoint）
⑤ 子 loop 结束，产出一段总结
⑥ 将总结包成 tool_result，以 ① 的调用 id 回送
   ↓
⑦ 模型收到结果
```

**模型并不知道"子 agent"是什么概念。** 在它看来 `spawn_subagent` 与 `read_file` 毫无区别——都是"发出一个调用，等一个结果"。二者的结构完全相同，差别只在 harness 侧实现的复杂度：前者去跑一整个 loop，后者去读一个文件。所以精确的说法是——**"子 agent"不是 agent 的一种能力，而是 harness 对某个工具调用的一种实现方式**，整个概念由 harness 构造，模型全程在状况之外。

```text
父 agent   thread_A ──> ckpt ──> ckpt ──> ckpt
                              │
                              └─ 该步为一次派生调用
                                        ↓
子 agent   thread_B ──> ckpt ──> ckpt ──> ckpt   （自身完整链）
```

父的链里只记录两件事：派出了任务、取回了结果。必须分开的三个理由：**避免上一节的并发竞争**（父子若写同一条链，两个执行者并发推进必然撞车）；**上下文隔离**（子 agent 的中间过程不应污染父的历史）；**可独立观察**（要查某个子 agent 做了什么，直接读它那条链）。

**监控的归属也由此确定：父 agent 不监控，harness 监控。** 父 agent（模型）眼中只有"一次耗时较久的工具调用"，子 agent 中间转了多少圈、调用了什么工具，它一概看不到——**这是刻意的上下文隔离**，若子 agent 的全部中间过程回灌到父的历史，父的上下文将迅速耗尽，隔离也就失去意义。真正实施监控的是 harness，它掌握每条链的状态、每条链的事件流、**状态聚合**（任一子链仍在运行则整个会话计为运行中）与**取消传播**（打断父时必须连带停止全部子链，否则会遗留无人认领的孤儿进程）。这正是[第一篇](/posts/agent-loop-harness/)那条判据的直接应用：需要跨线程的信息，必然在 harness。

同步与异步派发是这一层的设计选择：同步下父发出调用后阻塞等待，实现简单但父在此期间无法做别的事；异步下父派发后继续工作、子的结果以事件形式返回，吞吐显著更好，但父需要处理"结果稍后到达"，harness 也需要维护"哪些尚未返回"。

**注意这是两个层级的结构，不要混：** 链树表达"哪个 agent 派生了哪个"，每个链内部另有自己的 checkpoint 序列表达"这个 agent 走过哪些步"。

## 六、两个收尾问题

**序列化是维护成本的主要来源。** 两个反复出现的问题：**结构演进**——今天为状态新增一个字段，昨天存下的 checkpoint 里并没有这个字段，恢复旧会话时能否读出？处理不当就表现为"老会话全部打不开"，这也是需要专门迁移逻辑的原因；**格式选择**——通用文本格式可读但表达不了复杂对象，语言原生的序列化能存任意对象但跨版本可能读不出，而且反序列化不可信数据存在安全问题。

**双记录互为校验。** 另一种常见做法是在 checkpoint 之外并行写一份**可读的追加日志**（每轮一条，只追加不修改）。二者的失效模式不同：checkpoint 是结构化的、供恢复使用，但可能写坏（写到一半崩溃、序列化缺陷、结构变更）；追加日志格式极简、只追加不改写，损坏概率低得多。于是可以用日志作**权威基准**校验 checkpoint——比如比对两侧消息条数，发现 checkpoint 明显落后即判定需要修复，并从日志重建。

**这不是冗余存储，而是以一个不易损坏的东西去兜一个容易损坏的东西。**
