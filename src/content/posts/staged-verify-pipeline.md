我把自己在用的一个 skill 开源了：[staged-verify](https://github.com/yaofuhong0311/staged-verify)，一条给 AI 编码 agent 用的分阶段代码验证流水线。这篇讲它为什么长成这样。

## 一、"验证一下"这句话的三个坑

直接让 agent 验证刚写完的代码，通常会得到：跑一遍测试、说一句"看起来没问题"、结束。这里有三个结构性缺陷，而且都不是"prompt 写得更严格"能解决的。

**第一，作者自查。** 刚写完代码的那个会话，上下文里全是实现思路和自我辩护。让它 review 自己，等于让作者校对自己的稿子——不是它不认真，是它已经被自己那套推理说服了。这与我在 [Agent 工程系列](/posts/agent-evaluation/)里写过的"执行任务的那一个自评不算数"是同一件事。

**第二，只能测到已经写出来的东西。** 从代码出发推导测试用例——读函数、看参数、想边界——这条路很自然，但它有一个原理性的盲区：**测不出"这段逻辑本该写但根本没写"**。漏掉的那条校验不在代码里，你顺着代码走一百遍也遇不到它。

**第三，没有门。** 一次性对话没有"这一阶段不过就不许往下走"的约束，也没法中断之后接着跑。验证到一半上下文满了，前面的结论也就不成立了。

## 二、四道门

```
Phase 1          Phase 2                   Phase 3                     Phase 4
干净 review   →  冒烟+单测+覆盖率+效率  →  边界双轨(白盒+黑盒)+并发/故障  →  真实环境覆盖+效率对照
(零污染子代理)   (跑得起·对·测全·够快)     (代码出发 & 契约出发求差集)      (同一套用例指向集群)
```

每一阶段有明确的通过标准，**不通过就不推进；通过了也要停下来等人确认**才进下一阶段。状态落盘到 `.staged-verify/state.json`，支持断点续跑。

顺序是有讲究的：先冒烟后单测——**程序都起不来，单测绿了也没有意义**。

## 三、三个真正解决问题的设计

### ① 零污染 review

第一个坑的解法是把 review 放到一个**看不到本次会话任何历史**的全新上下文里。子代理天然满足这个条件——它只看到你在 prompt 里显式给它的东西。

但这里的规则必须写死，否则很容易失效：**只允许**传变更 diff、review 维度、输出格式；**严禁**传实现思路、设计讨论、"这段代码是为了……"之类的背景解释。

那些背景解释感觉上是在"帮助"review，实际正是要隔离的污染源——你一旦告诉它"这里这么写是因为要兼容旧接口"，它就不会再质疑这个前提了。代码需要的上下文，让子代理自己去仓库里读。

### ② 白盒黑盒双轨求差集

这是整个 skill 里最值钱的一条，也是第二个坑的唯一解法。

边界用例来自两条**正交**的轨道：

- **白盒轨**从代码出发：逐个读变更的函数，针对它实际接收的参数、调用的依赖、操作的共享状态推导用例。强在精准，但只能测到已实现的行为。
- **黑盒轨**从契约出发：给一个**看不到实现**的子代理，只喂接口签名或需求描述，让它独立推导"它应该接受什么、拒绝什么、处理什么"。

然后做一次**求差集**：

> **只在黑盒轨出现、白盒轨没有的用例 = 代码可能漏实现的高危项。**

漏写的校验、漏处理的分支，全在这个差集里。逐条回代码确认：真漏了就记为缺陷，确实实现了就补进套件。

关键在于黑盒轨必须**真的看不到实现**。只要给它贴一眼代码，它就退化成白盒轨了，差集立刻失去意义。这条约束和第一个设计是同一个原理——**隔离不是形式，是这个方法能成立的前提。**

### ③ 左移：同一条轨道，写前是图纸，写后是检查表

黑盒轨产出的那份"该处理/该拒绝"的清单，**写代码之前生成还是之后生成，内容是一样的**。

但用途完全不同：之后生成是检查表，判你写得对不对；**之前生成就是施工图纸，决定你写什么。**

所以流水线带了一个可选前置：还没动手写的时候，先把黑盒轨当 spec 跑一次，拿到的清单直接当实现待办照着写。同一个机制，**写前跑一次防 bug，写后跑一次兜 bug**——而预防永远比捕捉便宜。

## 四、几条不显然的约定

这些是踩过之后加进去的：

- **失败时说"继续"，一律理解为"重跑当前阶段"**，绝不推进。人在连点确认的时候是不看字的。
- **重跑上游会让下游失效。** 重跑 Phase 2 时，3 和 4 已通过的结论自动重置——它们建立在旧代码上。
- **flaky 不许"重跑一下就过"。** 时绿时红往往是真的竞态或 timing bug，尤其在流式、常驻进程、并发相关的改动里。要按缺陷定位根因，区分"测试没等够"还是"代码非确定性"。
- **并发用例必须真并发。** 线程池或异步同时发起，串行循环跑不出竞态，等于没测。
- **覆盖率只看本次变更行**，别被仓库整体覆盖率稀释。"未覆盖的变更行"清单是"你还没测到的角度"的客观依据——不靠猜，也不靠感觉。
- **真实环境的凭据不落盘。** 报告和状态文件里不得出现真实地址、令牌、认证头，一律用占位符和别名。

## 五、它和"三层防御"的关系

我之前写过[我的 AI Coding 工作流](/posts/ai-coding-workflow-2026/)，那套是三层防御：软约束（写进规则文件）、硬执行（钩子机械触发）、后置记录（经验沉淀）。

这条流水线补的是第四块：**验证**。前三层解决的是"别让它写出坏代码"，这一层解决的是"写完之后怎么确认它真的对"。

而它的核心思路，与我最近整理的 [Agent 工程系列](/posts/agent-reliability/)是一致的：**agent 的可靠性上限，取决于任务的"完成"能被多硬地检验。** 四个阶段其实就是把"这段代码写好了吗"这句语义判断，逐级翻译成一堆结构上可判的东西——冒烟的退出码、单测的通过数、覆盖率的未覆盖行清单、差集里的高危项、集群与本地的结果对照表。

**翻译得越彻底，"验证"这件事就越不依赖谁的手感。**
