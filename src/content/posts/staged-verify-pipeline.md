我把自己在用的一个 skill 开源了：[staged-verify](https://github.com/yaofuhong0311/staged-verify)，一条给 AI 编码 agent 用的分阶段代码验证流水线。这篇讲它为什么长成这样。

## 一、起因：出问题的不是编码，是理解

用 agent 写代码写多了会发现一件事：**它真正容易出问题的地方，不是把逻辑写错，而是对需求的理解本身就缺了一块**，而缺口大多落在边界上——某个入参为空没考虑、某个越权场景没想到、某个失败分支没处理、某个并发情况没想过。

这个区分很关键，因为**它决定了什么样的检查有用、什么样的必然无效**：

- 如果是**编码错误**（想对了写错了），那么读代码就能发现——代码和意图对不上。
- 如果是**理解缺口**（压根没想到），那么读代码**永远发现不了**——代码忠实地实现了那份不完整的理解，它内部完全自洽，没有任何矛盾可供察觉。**漏掉的那条校验不在代码里，你顺着代码走一百遍也遇不到它。**

做这个 skill 就是为了尽可能压缩第二类问题的发生。而一旦接受了"根因在理解、缺口在边界"这个判断，后面所有的设计取舍都是从它推出来的。

## 二、为什么常规做法救不了

直接让 agent"验证一下刚写的代码"，通常得到的是：跑一遍测试、说一句"看起来没问题"、结束。三个结构性缺陷，**每一个都能追回到上面那个根因**：

**第一，作者自查。** 刚写完代码的那个会话，上下文里装的正是**那份可能有缺口的理解**。让它 review 自己，它会拿同一份理解去对照同一份代码——当然对得上。这不是它不认真，是**两边的前提本来就是同一个**。

**第二，只能测到已经写出来的东西。** 从代码出发推导测试用例——读函数、看参数、想边界——这条路很自然，但它继承的仍然是那份理解。**白盒检查在原理上就发现不了"本该写但没写"**，理由同上。

**第三，没有门。** 一次性对话没有"这一阶段不过就不许往下走"的约束，也无法中断后接着跑。验证到一半上下文满了，前面的结论也就不成立了。

所以这件事不是"prompt 写得更严格"能解决的——**你需要一个不共享那份理解的独立信息源。**

## 三、四道门：为什么是四个、为什么是这个顺序

```
Phase 1          Phase 2                   Phase 3                     Phase 4
干净 review   →  冒烟+单测+覆盖率+效率  →  边界双轨(白盒+黑盒)+并发/故障  →  真实环境覆盖+效率对照
(零污染子代理)   (跑得起·对·测全·够快)     (代码出发 & 契约出发求差集)      (同一套用例指向集群)
```

分成四段不是为了看起来有条理，**顺序由两条约束同时定死：成本递增，依赖递增。**

| 阶段 | 前置条件 | 相对成本 |
|---|---|---|
| 1 静态 review | 无——代码存在即可 | 最低 |
| 2 冒烟 + 单测 | 程序得能跑起来 | 低 |
| 3 边界测试 | 得先有设计好的用例 | 中 |
| 4 真实环境 | 得先部署上去 | 最高 |

每一阶段都依赖前一阶段的产物或前提，而且一阶比一阶贵。所以**顺序不是随意排的——是"最便宜的筛子先过"**。同一个道理在阶段内部也成立：先冒烟后单测，因为**程序都起不来，单测绿了也没有意义**。

**而"门"的意义正在于此。** 如果不设门，Phase 1 挂了还继续往下走，后面三个阶段的工作全部作废——你在一份已知有问题的代码上做了最贵的那部分验证。早筛便宜，这是设门的全部理由。

**至于为什么每一道门都要停下来等人确认**——理由比"谨慎"要具体：**判断"这条失败是真 bug，还是测试本身写错了"是语义判断，agent 判不了。** 它手里只有结构信号（退出码、断言失败、diff），而"这个行为算不算符合预期"需要理解意图。这与我在 [Agent 工程系列](/posts/agent-reliability/)里反复写的那个缺口是同一件事，在这里以"必须有人拍板"的形式再次出现。

所以门不是形式主义，是**把 agent 判不了的那部分显式交还给人**。

## 四、三个设计，都在攻同一个根因

### ① 零污染 review：不让缺口传染

既然问题出在"那份理解可能有缺口"，那 review 就必须在一个**没有那份理解**的地方进行。子代理天然满足——它只看到你在 prompt 里显式给它的东西。

规则必须写死，否则很容易失效：**只允许**传变更 diff、review 维度、输出格式；**严禁**传实现思路、设计讨论、"这段代码是为了……"之类的背景解释。

那些背景解释感觉上是在"帮助"review，实际是**在把有缺口的那份理解原样复制过去**——你一旦告诉它"这里这么写是因为要兼容旧接口"，它就不会再质疑这个前提了。而那个前提，恰恰可能就是缺口本身。代码需要的上下文，让子代理自己去仓库里读。

### ② 白盒黑盒双轨求差集：造一个独立的信息源

这是整个 skill 里最值钱的一条，也是第一节那个根因的**唯一**解法。

既然从代码出发的检查继承了同一份理解，那就必须造一条**不经过代码**的路径：

- **白盒轨**从代码出发：逐个读变更的函数，针对它实际接收的参数、调用的依赖、操作的共享状态推导用例。精准，但只能测到已实现的行为。
- **黑盒轨**从契约出发：给一个**看不到实现**的子代理，只喂接口签名或需求描述，让它**独立重新推导一遍**"它应该接受什么、拒绝什么、处理什么"。

关键不在于"多了一种测法"，而在于**黑盒轨是重新理解了一次需求**——它没被第一次的理解锚住，所以它想到的边界可能是第一次漏掉的那些。

然后做一次**求差集**：

> **只在黑盒轨出现、白盒轨没有的用例 = 代码可能漏实现的高危项。**

这个差集就是"两份独立理解的分歧点"，而漏写的校验、漏处理的分支恰好全在里面。逐条回代码确认：真漏了记为缺陷，确实实现了就补进套件。

所以黑盒轨必须**真的看不到实现**。只要给它贴一眼代码，它就被锚住、退化成白盒轨了，两份理解重新变成一份，差集立刻归零。**隔离不是形式，是这个方法能成立的前提**——和第一个设计是同一个道理。

### ③ 左移：缺口在理解，那就在动手之前补

顺着这条线再往前推一步，会得到一个更划算的做法。

黑盒轨产出的那份"该处理/该拒绝"的清单，**写代码之前生成还是之后生成，内容是一样的**。但用途完全不同：之后生成是检查表，判你写得对不对；**之前生成就是施工图纸，决定你写什么。**

而既然根因是"理解需求时就缺了一块"，那**在动手写之前把那块补上，严格优于写完再回头抓**——写完再抓，缺口已经变成了代码、变成了基于它的其它代码，改动成本高得多。

所以流水线带了一个可选前置：还没动手写的时候，先把黑盒轨当 spec 跑一次，清单直接当实现待办照着写。同一个机制，**写前跑一次防 bug、写后跑一次兜 bug**——预防永远比捕捉便宜。

## 五、那些约定的来由

第四节这些规则单看像是过度讲究，其实每条背后都有具体理由：

- **失败时说"继续"，一律理解为"重跑当前阶段"。** 因为人在连续点确认的时候是不看字的，而这里点错的代价是"带着已知缺陷进入最贵的阶段"。
- **重跑上游会让下游失效。** Phase 2 重跑意味着代码变了，而 3、4 的结论是在旧代码上得出的——它们不是"还有效但需要复核"，是**已经失效**。
- **flaky 不许"重跑一下就过"。** 时绿时红往往是真的竞态或 timing bug，尤其在流式、常驻进程、并发相关的改动里。放行等于把一个真缺陷记成了噪声。
- **并发用例必须真并发。** 线程池或异步同时发起——串行循环跑不出竞态，那样的"并发测试"等于没测。
- **覆盖率只看本次变更行。** 仓库整体覆盖率会把新增代码的漏测稀释掉。而"未覆盖的变更行"清单的价值在于：它是**客观的**"你还没测到的角度"，不靠猜也不靠感觉——正好补上"想不到就测不到"这个根因的另一面。
- **真实环境的凭据不落盘。** 报告和状态文件里不得出现真实地址、令牌、认证头，一律用占位符和别名。

## 六、它补的是哪一块

我之前写过[我的 AI Coding 工作流](/posts/ai-coding-workflow-2026/)，那套是三层防御：软约束（写进规则文件）、硬执行（钩子机械触发）、后置记录（经验沉淀）。

三层解决的都是"别让它写出坏代码"，而这条流水线补的是**第四块：写完之后，怎么确认它真的理解对了**。

它的核心思路也和 [Agent 工程系列](/posts/agent-reliability/)一致：**agent 的可靠性上限，取决于任务的"完成"能被多硬地检验。** 四个阶段其实就是把"这段代码写好了吗"这句语义判断，逐级翻译成一堆结构上可判的东西——冒烟的退出码、单测的通过数、未覆盖的变更行清单、差集里的高危项、集群与本地的结果对照表。

**翻译得越彻底，"验证"这件事就越不依赖谁的手感。**
