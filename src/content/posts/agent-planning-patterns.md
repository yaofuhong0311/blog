> 本文是「Agent 工程」系列第 10 篇。

**先声明一件事：本篇的可靠度低于前九篇。** 前面讲的机制（loop 结构、调用与结果的配对、checkpoint、缓存前缀规则）都可以从接口文档与代码直接验证；**而规划模式更接近社区总结出的经验分类，边界本就模糊、不同来源讲法不一。** 所以本篇会对每条结论标注依据强度，文末附来源与依据强度表。

另外要先纠正一处我自己的框架偏差：前九篇始终把[第一篇](/posts/agent-loop-harness/)那个 while 循环当作"agent loop 就是这样"，**其实它只是其中一种模式（ReAct），而且不总是最优。**

## 一、五种模式

| 模式 | 机制 | 适用 |
|-|-|-|
| **ReAct**（推理 + 行动） | 思考 → 行动 → 观察交替迭代，直到判断信息足够。**每步一次模型调用** | 探索性任务、未知环境、每步结果决定下一步 |
| **Plan-and-Execute** | 一次性规划全部步骤，再顺序执行（常用更便宜的模型执行）；**失败时重新规划**。调用更少、成本更低，且计划在执行前可被检视 | 长的多阶段工作流 |
| **ReWOO**（无观察推理） | 三个模块：**规划器**在拿到任何工具响应之前，先编出一份带占位符、彼此关联的完整蓝图；**执行器**按蓝图调用工具收集证据；**求解器**把计划与证据配对，综合出答案 | 步骤可提前确定、彼此独立、可并行 |
| **Reflexion** | 每轮之后加入自我批判与记忆 | 需要迭代改进的任务 |
| **Tree-of-Thoughts** | 把中间思路当作搜索节点，按广度或深度策略探索多条候选路径 | 需要在多个解法间搜索比较 |

**ReWOO 的核心贡献是"解耦推理与观察"**——中间的工具结果不必回到规划器。论文称在一个多步推理基准上消耗效率提升约 5 倍且准确率更高，但这个数字**来自论文自述，不是第三方复现**。

**为什么 ReAct 的开销随轮数快速增长？** 这一条不需要引用，由[第一篇](/posts/agent-loop-harness/)那条"模型无状态、每轮重发完整历史"直接推出：ReAct 每步一次调用，第 N 轮那次请求要把前 N−1 轮内容全部重传——与 [checkpoint 全量快照](/posts/agent-checkpoint-storage/)的平方级增长同形。ReWOO 之所以省，正是因为**中间的工具结果根本不进入模型上下文**，只有规划与求解两次调用需要付费。

## 二、真正可操作的问题

这五个名字描述的是**倾向**而不是互斥的分类，真实系统几乎不会是纯粹的某一种——多个来源都指出多数生产系统组合使用多种模式。因此与其问"这个系统属于哪个模式"，不如把它当作一个**逐段重复出现的设计决策**：

```text
这一步做完之后，要不要回到模型再决策？

  要回    → 这一段呈 ReAct 形态（贵，但能适应）
  不用回  → 这一段可以批量或并行（省，但赌它不需要中途调整）
```

这个问题有明确答案，而且**在不同层级会得到不同答案**——同一个系统因此既像 ReAct、又带有批量执行的影子。**五个名字的价值在于为这个决策提供词汇**（"这里我们不回模型"），而不是给系统贴标签。（这条判据是本文的归纳，不是领域里的标准提法。）

顺带澄清一个易混点：**并行工具调用不等于 ReWOO。** 模型在一条回复里发出多个调用块，确实意味着"这几个动作是在没有任何观察的情况下决定的"，与 ReWOO 的核心思想相通；**但 ReWOO 是一个具有规划器、执行器、求解器三组件的完整架构，并行工具调用只是接口的一项特性。** 二者共享思想，不是同一个东西。

由此也能解释一个观察上的困惑：**"多轮"与"单轮内多个动作"是两个不同维度**——多轮之间模型重新决策（ReAct 的特征），单轮内的多个动作之间没有观察（批量的特征）。二者可以同时成立，而且真实系统中通常同时成立：整体多轮迭代，每一轮内部批量发起若干互不依赖的调用。

## 三、选择与取舍

"一次性规划"无法保证计划正确——但需要注意**ReAct 同样不能保证每一步正确**，它的每一步也是模型的判断。差别不在"会不会错"，而在**何时发现错了、以及那时浪费了多少**：ReAct 错一步即可察觉并调整；一次性规划则可能要到最后才发现，此前的执行全部作废。

**因此这是期望值计算，而不是正确性论证**：一次性规划赌的是"该类任务的规划出错概率足够低，低到省下的调用大于偶尔全废重来的代价"。

推论：**ReAct 是更安全的默认值**，一次性规划是一项优化——顺序不能反，应当先用 ReAct 把事做对、测出该类任务的规划稳定性之后，再考虑是否切换。而**"这类任务的规划稳不稳定"正是[上上篇](/posts/agent-evaluation/)那套评估要回答的问题**：没有那个数就是赌博，有了那个数才是工程决策。（本段为推断，非引用结论。）

两个降低风险的做法：**执行前先校验计划**——计划是结构化的（步骤加依赖），harness 可以在花钱执行前检查引用的工具是否存在、占位符是否对得上，这属于结构检查，很便宜；**某步失败即退回重规划**——这一退实际就成了 Plan-and-Execute。**所以 ReWOO 与 Plan-and-Execute 的边界本就模糊：一个赌不用改，一个准备好改。**

还有两处与本系列前面结论直接相关的观察：

- **Reflexion 有一个已知软肋。** [评估那篇](/posts/agent-evaluation/)已确立"执行任务的那一个自评不可信"——它已被自己的历史说服。因此自我批判环节**最好由独立上下文的评判者承担**，而这样一来它就退化成了一个独立评审节点。（此推论基于本系列前述结论，非外部材料。）
- **Tree-of-Thoughts 的形状此前已经出现过。** 把中间思路作为搜索节点、可回溯——与 [checkpoint 分叉](/posts/agent-checkpoint-chain/)同构，区别在于那里分叉是事后的调试与重试手段，这里分叉本身就是求解过程。代价是开销随分支数成倍增长。

## 四、依据强度

| 结论 | 依据 |
|-|-|
| ReWOO 的三段式与"解耦推理与观察" | **论文** arXiv:2305.18323，另有框架教程实现 |
| 效率提升 5 倍、准确率更高 | 论文自述，**非第三方复现** |

| ReAct 开销随轮数快速增长 | 由本系列第一篇直接推出，逻辑必然 |
| "要不要回到模型"作为统一判据 | **本文归纳**，非领域标准提法 |
| Reflexion 的自评软肋、ToT 与 checkpoint 分叉同构 | **基于本系列前述结论的推断**，非外部材料 |

**有一处材料我没有采信**：某来源在描述 Plan-and-Execute 时写"因为 agent 只规划一步，缺乏全局视野……"——该表述与它的核心定义（一次性规划全部步骤）自相矛盾，更像是在描述 ReAct 的短板，故未采用。**这也说明该领域的二手材料表述质量参差，引用时需要交叉验证。**
