## 一、四类，以及它们与"短期/长期"的关系

| 类型 | 装什么 | 一句话 |
|-|-|-|
| **工作记忆** | 当前的上下文窗口 | 会话绑定，**不持久化** |
| **情景记忆** | 过去发生过什么、什么顺序 | "上次那件事是这么发展的" |
| **语义记忆** | 事实与知识 | "什么**是**真的" |
| **程序记忆** | 规则、流程、技能 | "该**怎么**做" |

**"短期/长期"与四类不是两套体系，是同一套的两级粒度**：短期记忆就是工作记忆；长期记忆是后三类的总称。"短期/长期"只回答一个问题——**会不会跨会话存活**；四类分法在长期这一侧继续切了三刀，因为这三类的读写模式完全不同。

**只有"长期记忆"这个粗划分容易误导设计**：会做成一个统一的长期库，然后情景把语义淹没、程序记忆被做成"要检索才有"（而它本该常驻）。

有意思的是，**这四类在本系列前面都已出现过，只是没这么命名**：工作记忆就是[第一篇](/posts/agent-loop-harness/)那个消息数组；情景记忆就是 [checkpoint 链与追加日志](/posts/agent-checkpoint-chain/)；语义记忆就是[第五篇](/posts/agent-context-engineering/)讲的那种沉淀；程序记忆就是那篇四层里的系统提示、skill 与工具描述。**不是没做记忆，是已经在做，只是没按这个分类去想。**

需要提醒的是**术语边界是软的**：不同文章叫法有出入，有的以短期长期为主分类、四类为子分类，有的直接讲四类，有的还会加上多 agent 共享记忆。与[上一篇讲规划模式](/posts/agent-planning-patterns/)时一样，这属于**社区在收敛但尚未统一**的分类。知道这个出处与上述映射即可对话；**遇到别人用不同叫法，先问指的是哪一类，别假设同名同义。**

## 二、三类长期记忆的读写模式差得很远

以"维护一个项目的 agent"为例，同一件事在三类里的形态完全不同：

|  | 情景 | 语义 | 程序 |
|-|-|-|-|
| **例子** | "3/5 14:20 部署 v2.3 失败，报错连接被拒，操作序列是构建→迁移→部署，最终把迁移提前才成功" | "部署顺序必须迁移先于部署" | "遇到部署失败：先查连通性，再查权限，最后才怀疑代码" |
| **写入** | **自动、全量、不判断**——发生了就记 | **要判断值不值得**（第五篇那条判据：能否从环境重新推出） | **很少变，主要人工维护**，不是自动沉淀出来的 |
| **量** | 大，只增 | 小而精 | 小 |
| **召回** | 按时间、会话编号、相似情境 | 按相关性检索 | **几乎每次都用 → 适合常驻，而非检索** |
| **价值在** | 细节——保留"当时具体怎么回事" | 复用——不必每次重新推导 | 行为一致性 |

**语义与程序最容易混，区分方法**：语义是**一条事实**（"部署顺序是迁移先于部署"），程序是**一套行为方式**（"部署时按以下步骤检查……"）。

**程序记忆命中率高，因此按[第五篇](/posts/agent-context-engineering/)的命中率原则应当待在系统提示或 skill 里，而不是走检索**——把它做成"要查才有"，等于把一个常数时间的问题做成了一次检索。

## 三、三类的关系：一条提炼流水线

```text
情景（自动全量记录）
   │  ★ 巩固 —— 回看一批情景，提炼
   ↓
语义（少而精的结论）
   │  当某条语义反复被用来指导行为
   ↓
程序（固化成流程，写进提示词 / skill）

实例：
  情景：3/5、3/12、3/20 三次部署失败，都是同一个报错
     ↓ 巩固
  语义：「部署必须迁移先于部署」
     ↓ 反复用到，固化
  程序：写进系统提示 ——「执行部署时务必先运行迁移」
```

最后一步的效果值得注意：**一旦进了程序记忆（常驻提示词），就不再需要检索**——它每次都在。这正是"高命中率的东西该往前放"在记忆体系里的体现。

情景记忆本身有一个四阶段生命周期：**编码**（捕获一次事件及其完整上下文）、**检索**（把相关片段拉回工作记忆）、**巩固**（把累积的情景转化为持久的语义知识）、**淘汰**（存满时决定丢弃什么）。

其中第三步**回答了[第五篇](/posts/agent-context-engineering/)悬而未决的问题："谁来判断这条值得记"**——不是在事件发生的当下判断，而是**在巩固阶段回看一批情景之后再提炼**。而"回看一批"是跨会话的统计动作，按[第一篇](/posts/agent-loop-harness/)的判据属于 harness，与那时推出的结论一致，只是现在有了正式名称。**第四步淘汰则补上了那篇末尾"只写不删"的缺口**：它在这个框架里是一个显式阶段，而不是遗漏。

## 四、实现：判据不是"怎么标"，是"怎么查"

先说清楚一件事：**这个分类框架说"有这四类"，不规定怎么存**——就像"用户、订单、商品"是领域划分、不规定用几张表。所以工程实践很不统一：有的框架提供统一的记忆抽象、内部再分类型；有的只做"长期记忆"一个概念不细分；有的把情景记忆与 checkpoint 合并（**这其实合理**——它们本就是同一份数据的两种用法）。

| 方案 | 做法与代价 |
|-|-|
| **① 按目录或文件** | 情景与事实各一个目录，目录即分类；程序记忆不在此处（在提示词或 skill 里）。零机制、可直接读取与查找；量大之后不好召回 |
| **② 同一存储加类型字段** | 一张表按类型过滤。**通常会后悔**——三类查询模式差太远（按时间扫 / 按相关性检索 / 根本不查），一张表的索引与查询逻辑要同时迁就三种 |
| **③ 分开的存储** | 情景走只增的日志或 checkpoint 表；语义走带检索的库；程序走版本控制里的提示词与 skill 文件 |

**真正的判据不是"怎么标"，是"怎么查"：** 按时间或会话捞 → 只增的日志式存储；按"与当前任务相关"检索 → 需要检索能力；**根本不召回、一直都在 → 常驻提示词，别进任何库**。

落地前先回答三个问题：① 这条信息我会怎么召回（决定存哪）；② 它会不会过时、谁负责失效（决定要不要带来源与时间）；③ **它会不会直接改变 agent 的行为**（是 → 人工把关、进版本控制）。

**第三条是安全边界。** 程序记忆直接决定 agent 的行为，让它自动改写自己的行为规则风险很大——**能自动写入程序记忆的通道，就是持久化的后门**。[注入风险](/posts/agent-prompt-injection/)在这里被放大：一次注入如果能写进提示词，影响就不止那一次运行了。所以程序记忆通常人工把关、进版本控制，而不像语义记忆那样自动沉淀。

## 五、分开存会不会导致"还要组合"

不会，有两个原因。

其一，**组装上下文本来就是每轮都在做的事**，多几个来源不是新增工序。

其二更关键：**三类根本不落在上下文的同一个位置，谈不上"拼在一起"**——

```text
程序记忆  →  系统提示 / skill        常驻，在最前面
语义记忆  →  检索后注入到消息里       按需，在后面
情景记忆  →  通常不进上下文！         量太大，只在模型主动查时才读
```

而且**合并反而有害**，有两条具体理由：

- **破坏缓存前缀**——把每次都不同的检索结果写进系统提示，会使该段字节变化，按[前缀缓存那篇](/posts/agent-prompt-cache/)"前缀变了其后全废"，整条缓存作废。这正是那篇所列静默失效的又一种形态。
- **情景淹没语义**——情景自动全量、语义提炼精简，放在一起检索时召回结果会被大量情景细节占满，真正有用的结论反被挤出。

如果嫌"要管三个地方"，**正解是加一层门面而不是合并存储**：上层只调用一个统一的召回接口，内部路由到各自的存储。**这就是[第二篇](/posts/agent-tool-boundary/)那个 facade**——统一收口、底下可换实现。顾虑在接口层被消掉，而三类各自最合适的存储与召回方式被保留。

**这与[沙箱选型的结论](/posts/agent-runtime-sandbox/)完全一致：该统一的是接口，不是实现。**
