给一个沙箱分「2 核 4G」，这句话在容器和 microVM 上听起来一样，做的事完全不同。它要回答三个问题：**谁来强制这个额度、超限之后会发生什么、运行当中还能不能再改**。答案分别取决于两组对立——软限额与硬分区，可压缩资源与不可压缩资源。

## 一、软限额与硬分区

**容器是共享宿主内核 + cgroup 计量限额。** `cpu.max`、`memory.max` 这些上限，本质是内核里维护的普通数字，运行中可以实时改写。这里有个关键区分：cgroup 做的是**计量与封顶，不是预留**。它的四类语义各不相同——权重（`cpu.weight`，只在争用时才起作用）、上限（天花板，允许超卖）、保护（`memory.min`/`memory.low`，只承诺"不回收"而非提前占住）、以及真正意义上的独占分配（只有 `cpuset` 属于这一类）。

**microVM 是自带 guest 内核 + 固定虚拟硬件。** 开机时一次性定死机型（vCPU 数量、内存大小），guest 内核针对这套硬件建立页表与内存区域。它的上限是**结构性的**（相当于虚拟硅片），容器的上限是**策略旋钮**——这就是"容器能热改、能超卖，microVM 开机定死"的根本原因。

还有一个"谁当家"的差别值得点明：microVM 的 guest 在它那份固定额度**内部**自行分配和管理，有自己的内存管理、调度器、OOM killer，只是决定不了自己的总量（由外层 VMM 定）。容器没有自己的内核，**一切由共享的宿主内核管理**，cgroup 只是给它的用量封个顶——容器是一个"被限额的消费者"。

## 二、可压缩与不可压缩：为什么 CPU 超限只是变慢，内存超限却会被杀

这组对立的根子在物理属性：CPU 时间是可以切片发放的**速率**，所以可压缩；已经分配并且被真正触碰过的内存是**已经存在的状态**，没办法按需"部分取消分配"，所以不可压缩。

**CPU 超限的结果是节流，进程永远不会被杀。** 机制是内核的带宽控制：一个周期内（默认 100 毫秒）把配额烧光，组内线程就会被移出运行队列，一直等到下个周期配额补充才能继续跑——**哪怕这时候其他核心是空闲的**。可以从 `cpu.stat` 的 `nr_throttled`、`throttled_usec` 观察到。它的表现是周期性卡顿，伤的是尾延迟，但进程始终活着。

**内存超限的结果是被强制杀死。** 撞到 `memory.max` 时内核先尝试**回收**——丢掉页缓存、回写脏页、能换出就换出——回收之后仍然不够，才调用 OOM killer 发出 SIGKILL。在 K8s 里表现为 `OOMKilled` 与退出码 137。注意中间那步回收是一层缓冲，短暂超限不一定立刻就死。

有意思的是内存也有一个"软节流"档位：

| 配置 | 行为 | 会触发 OOM 吗 |
|-|-|-|
| `memory.high` | 进程被节流 + 加大回收压力（内存版本的 CPU 节流） | **永远不会** |
| `memory.max` | 撞上限且回收不出空间 → 调用 OOM killer | **会** |

三个容易误判的点：

- **退出码 137 泛指"被 SIGKILL"，不必然是 OOM。** 只有 `reason: OOMKilled` 这个字段才能把它和 liveness 探针失败等其他 SIGKILL 区分开。
- 原生 K8s 默认只根据内存 limit 设置 `memory.max`，`memory.high` 只在对应特性开启时才参与。
- cgroup v2 的 OOM 默认按分数杀单个进程，而 K8s 默认设置了整组一起杀，所以看到的是整个容器消失。

**"内存不可压缩"这个说法本身也需要一点修正。** 理论上内存也有一条压缩路径——把暂时不用的页面换出到磁盘，需要时再换回来（这与[第二篇](/posts/sandbox-page-fault/)讲的懒加载是同一套机制：触发缺页、读回内存）。这条路真实存在，但代价极大，磁盘访问比内存慢几个数量级，大量换页会让进程表现得如同卡死；而且 K8s 场景通常直接禁用交换分区，以免调度行为变得不可预测。所以更准确的说法是：**可压缩的那条退路在这个场景下被堵死了**，一旦撞上限又回收不出空间，剩下的选项就只有杀掉。

## 三、requests 与 limits：两个字段，四个作用

K8s 的 `requests` 通常被理解成"调度预留"——调度器按各 Pod 的 request 之和做装箱、挑节点。但它不止于此：运行时 kubelet 还会把 CPU request 翻译成 cgroup 权重，把内存 request 喂给 OOM 评分。`limits` 则是 cgroup 硬上限，但两种资源的落点完全不同：CPU limit 落到 `cpu.max`（主动节流，不杀），内存 limit 落到 `memory.max`（被动 OOM，可能瞬时越界后再被杀）。

QoS 等级由这两个字段的写法自动推导：limit 与 request 完全相等是 Guaranteed，设了 request 但不相等是 Burstable，什么都没设是 BestEffort。

这里有一组很容易被弄反的因果关系：**QoS 对 OOM 是直接控制，对驱逐则是涌现结果。** Guaranteed 的 OOM 评分被调到最受保护，BestEffort 最先被选中——这一段是 QoS 直接控制内核的 OOM 优先级。但节点压力**驱逐**的顺序，kubelet 文档明确说明不用 QoS 决定，而是按"用量是否超出 request、Pod 优先级、用量相对 request 的比例"来排。常见的那个 BestEffort → Burstable → Guaranteed 的驱逐次序是这套规则算出来的涌现结果，不是拿 QoS 当键值查出来的。

## 四、运行中还能不能改：一条不对称的分界线

容器这边，K8s 的原地扩缩容（KEP-1287）已经走完了从 Alpha 到正式发布的全过程。但它的能力是**不对称**的，而且这个不对称是机制必然：

- CPU 可以上调也可以下调，热改生效；
- 内存**上调**可以热改；
- 内存**下调**只能尽力而为——仅当实际用量已经低于新值时才收缩，否则就停在"调整中"状态。

原因正是前面那条"内存不可压缩"：内核没有办法强制回收正在使用的页。

microVM 这边更受限。vCPU 没有热插拔，运行中的实例加不了核。内存则有两条路：气球机制（inflate 时把页还给宿主、降低占用；deflate 时在预留上限内取回）以及较新的内存热插能力（可以涨到一个预先声明的上限）。气球机制单独使用时不能超过开机内存。还有一个实现细节值得记：气球 inflate 会触发相应事件，缺页处理逻辑必须把对应的页清零作废，否则下次缺页时会把陈旧数据重新发出去。

## 五、`/proc` 里的数字是假的：共享内核特有的陷阱

原生内核上，`/proc/meminfo`、`/proc/cpuinfo`、`nproc` 这些接口**不做命名空间隔离、也不感知 cgroup**。容器里读到的是整台宿主机的内存和 CPU 数量，而不是自己那份 `memory.max` 和 `cpu.max`。microVM 的 guest 在硬分区上启动自己的内核，它的 `/proc` 报告的正好是分配量，天然自洽——**这个陷阱是共享内核特有的产物**。

这个坑的经典受害者版本已经过时了，值得更新一下：

- **现代 JVM 默认已经感知容器**，读 cgroup 上限来定堆大小，不再从 `/proc/meminfo` 推算。但仍然可能 OOM——它只约束堆，进程总占用还是可能撞上 `memory.max`。
- **Go 的问题不是 OOM，是 CPU 过度并发导致节流**；较新版本的运行时已经会读取 `cpu.max` 并周期性重读。
- 缓解方式是用 downward API 把 limit 注入成环境变量，而不是让程序去读 `/proc`。

## 六、GPU：一个需要限定范围的结论

容器可以用 GPU：通过设备插件暴露资源名，配合运行时钩子，把设备节点和宿主驱动的用户态库挂进容器——本质是在隔离边界上为共享宿主驱动开了一个口子。已发布的 Firecracker 不行，因为它没有 PCI 总线，也就没有直通的可能。

但**这个缺口是"已发布的 Firecracker"特有的，不是 microVM 的通病**。Firecracker 有过单机多卡的原型验证，因人力原因暂停；而其他 VMM（Cloud Hypervisor、QEMU + VFIO、Kata）今天就支持 GPU 直通。业界的实际做法是分开处理：标准负载用 Firecracker，GPU 机器换成支持直通的 VMM。所以"GPU 场景偏好容器"是便利性与生态的取舍，而且换走了虚拟机级别的隔离，不是一条物理定律。

## 七、汇总与决策

| 维度 | 容器 / cgroup（软限额） | microVM / 硬分区 |
|-|-|-|
| CPU 超限 | 节流，进程活着只是变慢 | 固定 vCPU，guest 内核自行调度 |
| 内存超限 | 撞上限 → OOM Kill → 退出码 137；`memory.high` 只节流不杀 | guest 自己的 OOM killer，在开机定死的内存内 |
| 运行中调整 | 可热改；CPU 双向、内存上调即时，下调尽力而为 | vCPU 不能热插；内存靠气球或热插，封顶于预声明值 |
| 超卖 | 可以（上限之和大于节点容量），由内核运行时仲裁 | 更严格（真实预留），释放阀只有气球 |
| GPU | 可以：设备插件 + 共享宿主驱动 | 已发布的 Firecracker 不行；换 VMM 可以 |
| guest 看到的资源 | `/proc` 是宿主总量，容易错配 | `/proc` 正好是分配量，自洽 |

决策规则可以压成一句话：**需要弹性与生态（动态扩缩、GPU、超卖）就走容器；需要保证与隔离（硬下限、强信任边界、资源视图自洽）就走 microVM。**

而"2 核 4G"这句话在两条路线上的含义差别，正好是本篇的收尾：容器上它是一组可超卖的策略上限，空闲部分会被别人复用；microVM 上它是开机定死的真实预留，guest 在自己的 `/proc` 里就能看到这 2 核 4G。**真正的分水岭是"启动之后还想不想再改"**——容器改几个数字就行，microVM 则要么在预声明的上限内用气球和热插腾挪，要么用新规格重建实例（好在有快照机制，重建并不昂贵）。
