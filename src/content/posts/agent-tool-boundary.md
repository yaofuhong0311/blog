> 本文是「Agent 工程」系列第 2 篇。[上一篇](/posts/agent-loop-harness/)讲 loop 内部机制，落点是那行 `execute()`——整个 agent 唯一真正"动手"的位置。这一篇把它拆开。

围绕 `execute()` 有两个彼此独立、却常被混为一谈的问题：

| 问题 | 内容 |
|-|-|
| **① 暴露什么工具** | 给模型一个万能的 `bash`，还是 `read_file` / `edit_file` / `run_test` 一组专用工具 |
| **② 在哪里执行** | 本地起子进程，还是向远端沙箱发起请求 |

## 一、执行边界：为什么要把执行搬出去

本地执行意味着 loop 服务进程直接在自己所在的机器上派生子进程：

```python
# 进程内：loop 与工具执行同机、同进程树
subprocess.run("ls /tmp")

# 远程：执行被移出，交给专用沙箱
requests.post("http://sandbox/exec", json={"cmd": "ls /tmp"})
```

要把它移出去的理由是**威胁模型，不是工程整洁度**：命令由模型决定，而 loop 服务进程的环境里通常持有模型密钥、数据库口令与内部服务凭据。一旦 agent 被提示注入，"读取自身环境变量"这类操作在调用方代码看来与任何正常工具调用没有区别，会被照常执行。

**执行命令的进程与持有全部凭据的进程处于同一进程树、同一台机器**，这才是根本问题；同一个容器内的命名空间隔离并不改变这一点。远端沙箱的价值在于它不持有任何凭据、被破坏后可以直接丢弃重建。

**关键投资是接缝，而不是搬迁本身。** loop 侧只应该依赖一个抽象接口，底层实现在本地子进程与远程沙箱之间替换时，loop 无需改动。这与[沙箱番外篇](/posts/agent-runtime-sandbox/)里"统一收口 + 可替换后端"的 facade 是同一个模式在不同层的应用——那里替换的是沙箱引擎，这里替换的是本地执行与远程执行。

## 二、搬出去之后，白得的东西没了

真正的工作量不在远程调用本身，而在于：**原本靠"同进程、状态天然共享"白得的部分，现在必须被显式设计。**

最典型的失效是连续命令之间的依赖——`cd /app` 之后 `ls`，如果执行接口是无状态的，第一条命令起的 shell 已经退出，第二条在全新的 shell 里执行，工作目录回到默认值。同类失效还包括设置环境变量、加载脚本，以及任何"改变环境并期待后续命令可见"的操作。

这里的"状态"实际是两层，维持方式完全不同：

| 层级 | 包含 | 靠什么维持 |
|-|-|-|
| **沙箱级** | 文件系统、已安装的包、后台进程 | **同一个容器**存活即天然保持 |
| **shell 会话级** | 工作目录、环境变量、shell 函数、别名 | **同一个 shell 进程**；容器相同并不足够 |

**路由到同一个容器并不能让 `cd` 生效。** 工作目录是**进程**的属性而不是容器的属性——只要每次执行都派生新的 shell，它就会回到默认值。把这两层混为一谈，会得出"既然是同一个沙箱，状态自然连续"的错误结论。

维持 shell 会话状态有两条路：

**路径 A：维持一个长命 shell 进程。** 服务端保持一个不退出的 shell，命令写入它的输入流，输出从输出流读回。难点在于输出是连续字节流，**不存在天然的命令边界**——常见做法是在每条命令后追加一个哨兵标记，读到标记即判定结束；此外还要处理退出码获取、错误流分离，以及命令自身恰好包含哨兵字符串这类边界情况。

**路径 B：不维持 shell，由服务端自己记录工作目录。** 每次执行时拼接成"先切目录再执行"，执行后解析新的目录存回。实现显著简单，而且状态存在服务端存储而不是某个进程内，进程崩溃不影响状态；代价是 shell 函数、别名这类东西保不住。

实践中路径 B 更常见——agent 实际依赖的 shell 状态绝大部分只是工作目录和少量环境变量，为剩下那部分维持一个长命 shell 通常不划算。

## 三、路由：有状态的东西不能被负载均衡打散

上面两条路都以"后续请求确实落到同一个沙箱"为前提。**普通 Service 的轮询语义在这里是有害的**：它按设计把请求打散到不同实例，而有状态沙箱要求的恰恰是点名到固定实例——`cd` 发生在实例 A，后续的 `ls` 被轮询到实例 B 时，B 上不存在任何相关状态。

可行方案是给每个实例提供稳定标识（用无头服务加有状态副本集，拿到每个实例稳定的 DNS 名），或者由服务端自己维护一张"会话标识到沙箱地址"的映射表。

**这张映射表不能存裸 IP。** 实例重启后 IP 会变，缓存下来的旧值将指向不存在的地址，而且失效过程静默无告警。映射应当指向稳定名称并经 DNS 解析，或者具备感知实例变更的刷新机制——**"缓存一个本质会变的值"是这里最常见的缺陷形态**（这个错误在[网络那篇](/posts/sandbox-network-egress/)里也出现过，形式是把域名解析出来的 IP 写死进白名单）。

## 四、bash 还是专用工具：判据只有一句话

工具定义由调用方编写，并**随每次请求一同发送**——与消息同样是无状态的，模型不保留上一轮给过哪些工具。模型只能从这份列表中选择，依据仅有名字、描述与参数结构三者，所以描述应当写清**何时使用**，而不只是**它是什么**。

由此得到这个问题的正确提法：**工具面设计不是在优化模型的理解，而是在为自己的 harness 预留钩子。** 模型不了解你的安全边界、审批策略与界面形态，它只负责发出调用；而**调用的形状决定了 harness 能对它做什么**。`bash` 给了模型极大的动作覆盖面，却只给 harness 一个不透明的字符串，且所有动作形状相同；把某个动作提升为专用工具，等于为 harness 开出一个带类型参数的钩子。

以"删除文件前需要用户确认"为例。如果只提供 `bash`，harness 收到的是 `{"cmd": "rm /tmp/report.pdf"}`，判定是否为删除只能靠解析字符串，而删除的等价写法无法穷举：

```text
rm -rf /tmp/x
cd /tmp && rm x
find . -name '*.log' -delete
python -c 'import os; os.remove("x")'
> /tmp/report.pdf
mv /tmp/report.pdf /dev/null
```

**漏判是静默的**——不报错，只是没有拦住。如果提供专用的 `delete_file`，harness 收到的是结构化的名字与路径，按名字判定即可，不存在漏网路径。

值得提升为专用工具的，只有四类理由：

| 理由 | 说明 |
|-|-|
| **安全边界** | 难以撤销的动作（发信、调外部接口、删数据）需要门禁。专用的发信工具易于拦截，藏在 `bash` 里的一条网络请求无法拦截 |
| **陈旧检查** | 专用的编辑工具可以在写入前校验文件自上次读取后是否被改过，不满足就拒绝；这个不变量在 `bash` 上无法强制 |
| **渲染** | 部分动作需要专门界面。把"向用户提问"做成工具，才能渲染成弹窗、给出选项并阻塞 loop 等待回答 |
| **调度** | 只读工具可以标记为并行安全；同样的动作经由 `bash`，harness 无法区分并行安全的查找与并行不安全的推送，只能一律串行 |

**结论并不是"专用工具越多越好"。** 默认从 `bash` 起步以获得动作覆盖面；只有当需要拦截、渲染、审计或并行其中之一时，才把该动作提升为专用工具。每个专用工具都有成本：结构维护、上下文占用，而且工具过多会降低模型的选择准确率。**判据是一句话——harness 是否需要对这个动作做点特别的事。**

还有一条容易被忽略的推论：**边界只与工具列表一样紧。** "模型只能调用已定义的工具"在机制上成立——它除了输出调用块之外无法做任何事，而名字只能取自下发的列表。但只要列表里留着 `bash` 这类万能工具，专用工具上的门禁就被旁路了：为删除加的确认，一句 `bash("rm x")` 就绕过去了，而且**模型并非有意规避，只是判断这样更直接**。两种收口方式：不提供 `bash`，只给白名单动作（安全但能力受限，未覆盖的场景会卡住）；或者提供 `bash` 但对 `bash` 本身施加门禁，专用工具反而放行。

门禁也不必全部手写。工具可以配置权限策略，设成"每次询问"时，模型调用该工具会挂起等待允许或拒绝的回应，拒绝时还可以附上理由供模型读取并改换做法。**注意与 checkpoint 区分**：这里是执行前的审批门禁，checkpoint 指的是对话状态的持久化，二者无关。

顺带说，这条判据也解释了一类沙箱接口的划分方式：执行、文件、进程、外部工具代理各开一个原语，依据不是功能分类，而是上面那四类理由。文件读写不并入执行（不用 `cat`、`echo` 代替），是因为它需要路径级权限控制、二进制处理与大小限流，这些都是 harness 侧的管控能力，经由 `bash` 一概无法实施；进程独立于执行，除了生命周期模型不同，还因为长期进程需要可查询、可终止，而 `bash` 里后台启动之后这两项能力就没有了。**这类清单的本质是"为 harness 需要单独管控的对象各开一个钩子"。**

## 五、MCP：它改变的是工具定义的来源

先排除一个常见误解：**"工具背后是个远程服务"这件事不依赖 MCP**——手写工具定义、在实现里发起 HTTP 请求，同样是在调用服务。MCP 增加的不是"能调远程服务"这项能力。

它实际解决的问题是**工具定义由谁编写**。接入一个外部系统时，若没有标准协议，你需要为它的每个能力手写名字、描述、参数结构，并各自实现认证与返回值翻译；上游接口变更时还要同步维护。同一份工作会在不同团队、不同框架间重复，而且无法复用。

| 方式 | 工具定义的来源 |
|-|-|
| **自行实现** | 调用方逐个手写定义，并自行维护与上游的同步 |
| **MCP** | 服务端自我描述：连接后询问它有哪些工具，服务端返回完整定义，调用方直接置入请求 |

这个"询问即获得完整定义"的握手，是它之所以构成协议而不只是一个 HTTP 接口的原因。它标准化了两件事：**发现**与**调用**。

**MCP 不改变 loop，只改变工具定义的来源。** 接入之后 loop 无需任何改动：取得的定义照常置入工具列表，模型照常返回名字与参数，`execute()` 识别出这个名字属于 MCP 后转发给对应服务端，结果照常包装回送。**模型对 MCP 的存在毫无感知**——在它看来只是列表里多了几项，与手写工具没有区别。**MCP 是 harness 与工具提供方之间的协议，不是 harness 与模型之间的协议。**

最后两点实践提醒：一个 MCP 服务端通常暴露多个工具，接入一个可能使列表一次增加十余项，而**工具数量过多会稀释模型的选择准确率**，所以实践中通常需要按需启用一部分而不是全量置入；以及，**来自 MCP 不构成豁免理由**——一个能发起代码合并请求或写入外部系统的工具，属于"难以撤销的动作"，仍然要过前面那四类判据、仍然应该施加门禁。
