> 本文是「Agent 工程」系列第 8 篇。[上一篇](/posts/agent-reliability/)的结论是"完成"必须被改造成可检验的。这一篇是它的放大版：当范围从"单次任务是否完成"扩大到"整个系统是否变好"，同样的困难会以更大的规模重现。

## 一、"跑几个例子看看"为什么不成立

改完系统提示后手动试三个例子、感觉不错就上线——这个做法有两个问题，第二个更隐蔽。

**问题一：模型是非确定性的，跑一次的结果几乎不提供信息。** 同一输入同一提示跑五次，可能三次完美、一次打转失败、一次完成但多改了不该改的文件——**这不是缺陷，是它的正常行为**。由此得到一个必须先接受的推论：**agent 的评估结果不是"通过/不通过"，而是一个通过率。** 改动前跑 20 次通过 14 次、改动后通过 16 次，这点差距很可能只是噪声。

**单测是断言，agent 评估是测量**——两者的思维方式不同，这是本篇所有内容的前提。

**问题二：你手动试的用例是你想得到的场景。** 而 agent 真正出问题的地方，恰恰是你没想到的那些——奇怪的输入、没预料的文件格式、比设想多绕一层的任务。所以"我试了几个都挺好"这句话的信息量接近于零。

## 二、评估集做不到什么

必须先承认三件事：它**不能证明"变好了"**（用例集永远覆盖不了真实输入空间）、**不能预测新场景**、**过了评估集不代表线上没问题**（反之亦然）。agent 比传统软件更难的地方在于输入空间开放、行为是分布而不是确定值。

但结论应当是**调整定位**而不是放弃：**评估集是"防止已知的坏事重演"的工具，不是"证明系统好"的工具。**

这个标准低得多，却是真能做到的那个。类比单测——它同样从不证明代码正确，只防止改 A 时弄坏 B，而大家早已接受它的定位是回归防护而非正确性证明。agent 评估集的唯一可靠价值是：**上次那个坑，别再掉进去第二次。**

评估集的来源也很朴素：**从真实的失败里来，每一次线上失败都该变成评估集里的一个用例。** 手写想象出来的用例价值远低于真实失败——后者已经证明了"这里模型确实会错"，前者大概率是模型本来就不会错的。

```text
线上出问题 → 固化进评估集 → 改 → 用整个评估集验证
                                      ↓
                          确认这次修好了，且没弄坏别的
```

**"没弄坏别的"才是重点。** 打转干预、提示词约束——每一条都可能在修好 A 的同时弄坏 B，而没有评估集，你不会发现 B 坏了，直到线上再炸一次。

## 三、三堵墙：只有一堵能靠加样本翻过去

"样本不够"常被当成唯一原因，实际这里是三个性质不同的障碍：

| 墙 | 内容 | 加样本管用吗 |
|-|-|-|
| **方差** | 同一用例跑 N 次得到一个分布，跑得越多估计越准 | **管用**，但代价实在——要区分 70% 与 80% 且有把握，大约需要每版本几百次量级；而每次运行是一整个会话、可能几十次模型调用 |
| **覆盖** | 你的用例不代表真实输入分布 | **不管用**——同一用例跑 1000 次，对没放进去的场景信息量仍是零。加"重复次数"与加"用例种类"是两件事 |
| **标注** | 就算前两堵都过了，你还得知道每次运行算不算成功 | **不管用**——没有标签的样本再多也算不出通过率 |

第三堵墙就是[上一篇](/posts/agent-reliability/)那个语义缺口，它在这里换了个形式再次出现。

## 四、三层评估栈：离线只是最窄的一层

| 层 | 测什么 | 覆盖面 | 反馈速度 |
|-|-|-|-|
| 离线评估集 | 已知的失败模式 | 窄——只有你放进去的 | **快**，改完就能跑，能拦在上线前 |
| 线上指标 | 真实分布 | **宽**——就是真实输入 | 慢，事后 |
| 用户信号 | 用户是否满意 | 宽，而且是**免费的真实标签** | 慢 |

**线上把三堵墙同时降低了**：样本由真实流量提供、分布天然真实、部分标签由用户行为自带。代价是慢且事后。所以二者不是二选一，而是一前一后——**离线是改动前的快速门禁（窄但快），线上是改动后的真实测量（宽但事后）**。

另有一批线上指标**不需要知道正确答案就能算**，只需与上个版本相比：完成率、轮数分布（中位数 8 轮突然变 15 轮就是退化信号）、打转检测命中率、人工接管率。

## 五、评估属于 harness，而且基本是免费的副产品

按[第一篇](/posts/agent-loop-harness/)那条判据即可定位：评估本质是**跨运行的比较**，而跨运行的信息只有 harness 有。更关键的是——**harness 不需要为此新建一套系统，它本来就在数据通路上**，这些数据是顺手就有的。

| 能力 | 说明 |
|-|-|
| **免费指标** | 轮数、消耗、耗时、工具调用序列与失败率、打转检测命中率、终局是正常结束还是触顶还是停下问人——均无需知道正确答案，与上版相比即有信号 |
| **免费标签** | 任务有机器可检验目标时，[终局校验](/posts/agent-reliability/)本就会跑——于是**线上每一次真实运行都顺手带上了成功或失败的标签**，第三堵墙在这类任务上被顺手拆掉 |
| **评估集自我生长** | 检测到失败即自动把该次运行的初始状态固化入库；而"初始状态"早已存在——**就是 [checkpoint 链](/posts/agent-checkpoint-chain/)的第一个节点** |
| **重放能力** | "重放一个评估用例"在实现上就是从存好的 checkpoint 起一条新分支（就是那个重放机制，只不过这次用于评估而非恢复） |
| **A/B 与影子运行** | harness 掌握"用哪个版本的提示与工具集"：可以灰度，也可以**影子运行**——同一输入让新版本在后台也跑一遍、结果不给用户看，只用于对比 |

**影子运行基本消解了"离线评估集覆盖窄"这个问题**：输入是真实的，代价只是多花一份计算。**checkpoint 链在这里第二次派上用场**——它本为恢复而设计，顺带成了一个完整的评估语料库。

但要诚实：**语义判断仍未解决。** harness 能算轮数、能跑测试、能比指标，"这份报告写得好不好"它依然判不了。那个缺口不会因为埋点做得好就消失，只是被推到了"没有机器可检验目标"的那部分任务上。

## 六、没有基准，怎么判断一个提示词的好坏

关键在于：**你要回答的从来不是"这个提示词有多好"，而是"新的比旧的好吗"。** 改提示词的决策永远是二选一，不是打分。**因此基准不需要外部提供——上一版就是基准。**

**配对比较在统计上强得多。** 非配对（两组不同输入分别跑）的噪声有两个来源：版本差异加**输入本身难易不同**，而后者常常盖过前者；配对（同一输入两版各跑一次）消掉了输入难易这个噪声源，剩下的差异更纯粹地来自版本。**同样的把握，配对所需样本量比非配对少一个量级**——而配对样本恰恰由影子运行免费产出。统计口径也随之改变：数"新版赢了多少次"，而不是比较两个总体的平均值。

比什么？有机器判据的任务直接比那些免费标签与指标；没有机器判据的任务（写报告、做分析）有两条不需要绝对基准的路：

- **用户行为当标签**——重问等于没答好、点重新生成等于不满意、手动改动等于差一点、直接采用等于够好。全部免费且真实。
- **成对偏好判断**——同一输入下两版产出并排给独立评判者，问"哪个更好"。

**成对偏好比绝对打分可靠得多。** "给这份报告打几分"缺乏稳定性、会随时间漂移、不同评判者标准不一；"A 和 B 哪个更好"则稳定得多——它不需要任何标尺，只需要能分辨高下。

不过要看清它的盲区：**相对比较解决"哪个更好"，解决不了"够不够好"。** 有两个真实风险：可能一直在局部最优里爬（每版都比上版好一点，但整条路线本就走偏，察觉不到）；也可能所有版本都很差（A 比 B 好，不代表 A 能用）。要回答"够不够好"最终仍需外部参照——人工抽样评估或真正的基准集。**但这件事的频率可以低得多**：日常迭代靠相对比较（便宜、快、自动），隔一段时间做一次绝对校准（贵，不必每次都做）。**绝对好坏这个问题是被降频了，不是被解决了。**

## 七、"好"不是被发现的，是被定义的

没有客观标准躺在那里等着被测出来。**"定义好坏"就是把上一篇那个动作再做一遍**——那里翻译的是单次任务的"完成"，这里翻译的是整个系统的"好"。三种实际的定义方式：

| 方式 | 说明 |
|-|-|
| **用业务后果定义** | 不问"agent 好不好"，问"用户有没有拿到他要的东西"——任务完成率、人工接管率、用户重试率。**这些不是"好"的代理指标，它们就是"好"的定义**：90% 的用户无需干预即拿到结果，那就是好 |
| **跟人比** | 同一批任务让人做一遍，比质量与耗时——给出一个真正的绝对参照点 |
| **跟"不用 agent"比** | 最容易被忘：真正的基线往往不是另一版 agent，而是现状。如果现状是"这事没人做"，做到 60% 已经是净收益 |

一个实操捷径：**先定义"坏"。** 列举"什么算好"很难，列举"什么算失败"容易得多——改错了不该改的文件、打转超过 N 轮、声称完成但测试没过、用户不得不重问。这几条现在就能写出来，而"什么叫好的产出"可能想半天。写完之后**"好"就等于"这些都不发生"**，而且这份清单天然就是评估集的骨架，每条对应一个可检测信号，这些信号 harness 大多顺手就有。

最后澄清一个容易被拿来否定整件事的说法：**"由人定义"不等于"主观"。** 二者中间隔着的正是"拍板定义标准"这一步——**拍板是人的判断，拍完之后的一切都是可测量的**。类比考试及格线：定 60 分是人拍的，但"你考了 73 分"是客观事实，不因谁来看而改变。**选标准主观，执行标准客观。** 这个模式在工程里到处都是，服务可用性指标定在几个九同样是拍的，达没达到则是可测的。

这个区分决定了三件事能不能做：检测退化（纯主观则"这版比上版差"无法成立）、自动化（凭感觉的东西写不进代码）、交接（标准若只在某人脑子里，换人即失）。

确实存在翻译不掉的部分（文案有没有味道、报告写得好不好）。处理办法是**降低其主观性而不是假装它客观**：成对偏好优于绝对打分；多个独立评判者取多数以平掉单次判断的噪声；降频抽样而非每次都判。**这些不能把主观变成客观，但能让它可复现**——同一批产出今天判与下周判结论基本一致，而可复现就已经足够用来决策。

**而且这不是 agent 特有的困境。** "代码质量好不好"同样是定义出来的——覆盖率多少、检查规则怎么设、评审过几人，标准同样由人拍，却没人因此说代码质量没法管。agent 评估显得格外虚，主要是因为这块太新、行业尚未形成默认接受的那套标准，**而不是它本质上更主观**。卡住多数团队的也不是"测不准"，而是**从未走完"拍板定义"这一步**——定义为空，测量就为空。

```text
你拍板：「好」的定义是什么（业务后果 / 对比人 / 对比现状）
   ↓ 翻译成可检测的信号
harness 顺手采集（它本就在数据通路上）
   ↓
日常迭代靠配对比较（快、便宜、自动）
隔一段时间做一次绝对校准（贵，低频）
```
