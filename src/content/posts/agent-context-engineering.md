> 本文是「Agent 工程」系列第 5 篇。前四篇解决的是机制——loop 如何运转、工具边界划在哪里、状态如何持久化。这一篇解决的是**往这台机器里放什么**。

首次请求发出时，系统提示与消息中通常已经装有身份与行事规则、工具说明书、项目上下文、长期记忆、临时检索的资料，其总量往往远超对话本身，而且全部与对话争夺同一个上下文窗口——**放得越多可对话的轮数越少，放得不对则行为走偏**。

## 一、一条指令该不该写：判据是"不写会怎样"

长系统提示的代价不止于额度成本，有两点常被低估。

**系统提示通常不参与压缩。** 压缩处理的是累积的对话历史，而系统提示是每次请求原样重发的固定前缀，不会被压缩掉——它不是"迟早会被压缩掉的负担"，而是**每一次请求都要付、永不减少的固定税**。对话越长、请求次数越多，这笔税交得越多。

其次是**首尾效应**：内容越长，位于中部的部分被真正"看见"的程度越低。所以位置也是变量，而不只是长度——同一条指令放在大段内容中间与放在末尾，效果不同。

最反直觉的一条：**每加一条指令，都在稀释已有的每一条。** 多数人对提示词的直觉是加法——"写了就有约束，不写就没有，加一条只是多一个约束"。更接近实际的模型是：**注意力总量有限，所有指令争夺同一份注意力。** 5 条指令时每条都显眼；50 条时每条的分量被摊薄，模型开始按自己的判断挑重点执行。常见症状是：堆砌大量"必须""禁止"之后，模型开始过度触发——在一堆同等强度的强制指令中它分不清何者真正要紧，只好一律从严。

因此下笔前的判据是——**这条不写，会发生什么？**

- 不写模型也会那么做 → **删掉**。这是多数提示词里的冗余：写了一堆模型本就会遵守的常识。
- 不写模型行为会变糟 → 留下。
- 不确定 → 说明从未验证过，**先删掉试试**；若行为无变化，说明它一直在无谓占用注意力。

关键在于判断依据是**实测的行为差异**，而不是"读起来是否周全"。一条读来合理全面、删掉后行为却毫无变化的指令，是纯粹的负担——占额度、稀释他条，还给人一种"已经约束住了"的错觉。

## 二、该放在哪：四层，按命中率

同一条信息可以放在四个位置，选择依据是**命中率**——它在多大比例的请求中真正被需要。

| 放哪 | 装什么 | 何时被读到 |
|-|-|-|
| **系统提示** | 跨所有任务都成立的：身份、总体行事风格、硬性禁令 | **每次请求，永远** |
| **工具描述** | 这一个工具在什么情况下用、怎么用 | 每次请求，但仅在考虑该工具时起作用 |
| **skill** | 特定任务才需要的流程与知识 | **描述常驻，正文按需加载** |
| **运行时注入** | 本次运行才知道的事实：目录结构、检索到的资料、用户数据 | 仅在需要的那一次 |

**"何时该用某工具"应该写在该工具自己的描述里，而不是系统提示里**，有四个机制性理由：**① 就近**——模型判断是否使用该工具时，描述就贴在旁边，写进系统提示则规则与被约束对象相分离；**② 不占全局注意力**——写进系统提示就是投入全局竞争池，与身份、风格、禁令争夺同一份注意力；**③ 随工具数量扩展**——20 个工具各写一条，系统提示会退化成一份工具手册，而任一轮对话中其中 19 条都无关；**④ 跟着工具走**——工具可以动态增减（尤其是外部协议提供的那些自带描述，无法提前写进系统提示），规则随工具装载与卸载才是自洽的，否则工具卸载后规则仍留在原处成为纯噪音。

**核心原则：把内容放在"最靠近它被需要的那一刻"的位置。** 放得越靠前（越全局），付出的固定成本越高、对其余内容的稀释越强。skill 的渐进披露设计正为此——让一份很长的流程文档平时只占一行描述的位置，真用上时才展开，同时满足"写得清楚"与"不必每次付全额税"。

## 三、材料如何进入：push 与 pull

指令之外的另一半是完成任务所需的材料。以"在几万文件的代码库中回答『登录逻辑在哪』"为例，存在两种根本不同的做法：**push**——你的代码先检索，把结果拼进消息一并发出；**pull**——你给出查找、读取、列目录等工具，模型自行按需取用、逐步聚焦。

**分界不在技术手段（用查找还是用向量检索），而在"谁在什么时候决定要什么"。** 同一条查找命令，由你预先执行并塞入即为 push，由模型在过程中发起即为 pull。这里的 pull 与"拉取最新数据"无关，指的是**信息不被预先塞入，而由模型主动取用**。

| 维度 | push | pull |
|-|-|-|
| 谁判断相关性 | 检索代码，**在模型看到任务之前**——只能靠字面相似度猜 | 模型，**在理解任务之后**；找错了还能换个词再找 |
| 相关性 | 差 | **好** |
| 延迟 | **好**，一次往返 | 差，多轮往返 |
| 成本 | **好** | 差——每轮都要重发全部历史，第 5 轮时前 4 轮攒的内容全部重传 |

**pull 不是"更高效"，它更准但显著更慢更贵。** 常见误读是把相关性优势当成效率优势，进而认为 push 可以被淘汰。实际取舍是：**pull 赢在准确，push 赢在快和便宜。**

**而且这是设计期决策，不是运行时判断。** 模型不会"决定本次用 push 还是 pull"——推什么由你组装请求的代码写死，拉什么由你挂了哪些工具决定；**你定下限，模型决定是否越过它**。实际系统几乎都是混合——**把"它反正一定会去查的东西"提前推入**（比如目录结构），用少量固定额度换掉开头几轮必然发生的探索往返。

判据还可以再向下推进一层。两类任务对"全貌"的要求不同：

- **总结一份文档**——必须读完每一部分，没读过的段落无法被总结。**这个全貌不可压缩**，给一份目录代替不了内容。
- **在代码库中定位登录逻辑**——无需读完几万文件，需要的是**指路能力**。一次关键词查找返回的几十行就是此场景的全貌，足以判断该去看哪个文件。

所以**pull 并非"看不到全貌"，而是分层地看**：先取一份低分辨率全貌（查找结果、目录树，几十行，便宜），选中局部后再取高分辨率细节（读那几个文件，贵但只读选中的）。**查找、列目录这类工具本质上是"低分辨率全貌生成器"。** 判据因此可以更新为：**这个全貌能否压缩成一个足够指路的低分辨率版本？** 不能（总结、翻译、通读审查）→ push；能（在大集合中找特定的东西）→ pull。

注意**能否压缩取决于任务而不是数据大小**：同一个代码库，"登录逻辑在哪"能压缩，"整体架构是什么"压不掉——要讲架构就得看过足够多的地方。

## 四、污染必然发生，重点在治理

随着会话推进，历史中会累积：命中大半无用的查找结果、读完发现是废弃代码的 800 行全文、失败测试的 2000 行堆栈、没命中的空查询。**它们全部留存，且每轮请求完整重发。** 前两个后果可以直接推出——成本，以及与第一节同构的注意力稀释。第三个最隐蔽：

**陈旧上下文：历史会同时陈述两件矛盾的事。** 第 5 轮读某个文件得到内容 A，第 15 轮改写该文件使其变为 B，第 25 轮模型需要该文件内容时往上翻，看到第 5 轮那份完整的 A 并据以推理——**而 A 已经过时**。旧内容不会自动消失，也没有任何标记说明它已失效。**这不是模型犯错**：从它的输入看，A 确实是它亲眼读到的。根因是**上下文这个数据结构没有"失效"概念——只增不减，新旧平等并存**。（[第二篇](/posts/agent-tool-boundary/)里"陈旧检查"作为提升为专用工具的理由之一，防的正是这件事。）

| 手段 | 做什么 | 代价 |
|-|-|-|
| **清除工具结果** | 清除老的工具结果（是删，不是总结） | 信息真的没了，之后要用需重新取 |
| **压缩** | 将早期历史总结压缩为摘要 | 摘要必然有损 |
| **工具输出卸载** | 大输出落盘为文件，上下文里只留路径与预览 | 需要细节时多一次读取 |
| **子 agent** | 把探索过程整体隔离出去 | 多一层往返与协调 |

**子 agent 被低估的一面：它是一道上下文防火墙。** 不用它时，探索期的 40 次查找、读了又丢的 6 个文件永久堆在主上下文中；用它时，子 agent 在自己的链里反复检索（弄脏的是它自己的上下文，用完即丢），只把一段结论交回，主上下文仅多出一对调用与结果。

**这解释了一个常见现象**：让主 agent 直接大范围探索，跑到后期开始答非所问；改为派子 agent 探索、只收结论则表现清醒得多——**不是模型能力的差别，是上下文干净程度的差别。**

最后要澄清：**污染与推拉无关。** push 同样污染——塞入 20 段检索结果其中 17 段无用，那 17 段照样占位、稀释注意力、每轮重传。差别在污染的**形状**：push 的污染**可预测**（量由你定）但**难以归因清理**（混在你组装的消息里，与有用内容长得一样）且**躲不掉**（按定义就发生在主上下文）；pull 的污染**不可预测**（可能 3 轮也可能 30 轮）但**每块都带出处**（属于哪次调用）因而可被规则精确清除，而且**可以外包给子 agent**。

**结论：污染必然发生，设计重点在治理而非避免**——控制入口（大文件先截断、大输出卸载为路径）、保留可清理性（进来的东西带上出处标记）、能隔离就隔离。推拉选择解决的是**相关性**问题，它影响污染的严重程度，但不改变污染必然发生这一事实。

## 五、memory：跨会话的沉淀

先与 checkpoint 划清界线，二者解决的问题不同：**checkpoint 服务于同一条会话内的续跑**，存的是完整快照，目标是还原"当时的完整状态"；**memory 服务于跨会话的沉淀**，存的是提炼后的内容，目标是把"学到的东西"带到全新的上下文中去。

最直觉的做法——把上次会话的消息直接读进来——立刻失效：上次攒了 5 万额度，这次一开局就用光；其中九成是过程中的废弃物；跑过 10 次会话后更无从选择加载哪一次。**memory 因此必须是有选择、被压缩过的：它不是"保留历史"，而是从历史中提炼出值得带走的东西。**

四个真问题：

**① 写什么。** 值得记的通常是：用户的稳定偏好、被纠正过的错误、验证过的做法、不易从代码或文档直接看出的约束。反之，**代码库里已写明、提交历史里能查到的都不该记**——那是重复，而且会过时。

**② 何时写。** 会话结束统一总结（简单，但会话崩溃即丢失）还是过程中随时写（及时，但需要模型自行判断"这条值得记"）。

**③ 如何召回。** 全部推入则记忆一多即爆；只给搜索工具则慢、而且模型未必知道该搜什么；**推摘要加拉正文**——每条记忆只推一行描述，需要时再读全文。**这正是 skill 的渐进披露模式，也是上一节的推拉混合，同一套路第三次出现。**

**④ 如何防止过时。** 跨会话使陈旧问题比第四节的更严重：三周前记下的"部署要先跑某一步"可能早已不对，而**没有任何机制会主动告知它已失效**。

那么谁来判断"这条值得记"？两个极端各有失效模式：**代码定规则**可预测、可审计，但**规则写不全**——真正值得记的往往恰恰是你事先没预见到的，而"预见到了"就说明它不是意外；**模型自行判断**能捕捉到意外，但不稳定且**倾向于多记**，几十次会话后即成噪音。实践取第三条：**把规则写成判据交给模型逐条套用。**

**而判据必须可在当下判断，不能要求预测未来。** "下次会不会再遇到"是个好记的口号，但模型无法预知未来、甚至不知道存在"下次"。它实际能判断的是该信息本身的性质——**这条能否从环境里重新看出来？** 能（写在代码、文档、提交历史、目录结构里）→ 不记，下次自己看即可，记了反而会过时；不能（只存在于本次对话，尤其是用户口头给出的）→ 记。

注意这与第一节的判据同形：两处都拒绝"看起来是否周全"，都要求"实际有无差别"。

**最强的信号是用户的纠正**，因为它**完全不需要预测未来**——模型只需观察到"我刚才判断错了并被纠正"这一当下事实，而该事件本身同时证明两件事：我的先验是错的（否则不会被纠正），且这条信息推不出来（能推出来就不会错）。两个条件同时成立，必然值得记。次强的信号是**反复出现的操作**与**踩过的坑**；一次性事实基本不值得记——下次自己看便知。

还有一条容易搞错的分工：**"跨会话"的判断本就不该交给模型。** "这件事在过去 10 次会话里出现过几次"是跨会话信息，按[第一篇](/posts/agent-loop-harness/)的判据**根本不在模型的输入之内**——指望模型判断它，与指望它监控子 agent 属于同一类错误。正确分工是：**模型**判断"这条能否被重新推导出来"（只需看信息本身）；**harness** 负责识别纠正模式、跨会话计数、回收复查（写下来很久没被读到的记忆标出待删）——这些对 harness 而言只是普通的查库或读目录，没有任何特殊机制。

一个实用实现：**把 memory 做成文件。** agent 写 Markdown，下次会话用现成的读取与查找工具取用。好处是**不需要任何新机制**——不必建向量库、不必设计新接口，它就是文件，复用已有的工具面；召回也自然分层：目录列表是低分辨率全貌，具体文件是高分辨率细节。

最后，光有"写"不够，还必须有"删"：过时的、事后发现是错的、写完再没用上的都要能清掉，而"何时该删"比"何时该写"更难判断，因为没有信号会主动告知失效。实践中的兜底很朴素：**一条记忆一个文件，并写明它为什么成立**——将来复查时可以判断"它当时成立的前提现在是否还在"。**记下"为什么"比记下"是什么"更抗过时。**
