> 本文是「沙箱底层机制」系列第 12 篇。[上一篇](/posts/sandbox-one-decision/)把七个角度收束成了一个决策。这一篇换个方向：拿这套框架去看一个真实产品，检验它对不对得上。

案例是 **AgentENV**——清华 MADSys 实验室联合月之暗面等单位于 2026 年 7 月开源的 Agentic RL 执行环境平台。选它是因为它几乎逐条踩在前面那七个角度上：隔离用 Firecracker、启动用快照、资源靠回收与超卖、存储走远端按需加载，而**镜像模型直接解掉了[第八篇](/posts/sandbox-image-layering/)那个明确的缺口**。

## 一、为什么训练场景要另造一套

它的三条场景约束，第三条是全篇的经济学基础：

| 约束 | 为什么是 Agentic RL 特有的 |
|---|---|
| **强隔离** | 模型受奖励驱动，会主动尝试越界——改评测逻辑、读答案、访问隐藏服务。**这首先不是安全问题，是训练信号被污染的问题**：越界成功会被当作"任务完成"计入奖励，模型学到的是错误策略 |
| **海量镜像** | 每个任务有各自的运行时、工具链、代码仓库、依赖版本，镜像总量可远超单节点磁盘容量，不可能预热到每台机器 |
| **绝大多数时间空闲** | 环境的时间几乎都花在**等模型生成下一步动作**上。数千个环境同时"存在"，同一时刻真正在计算的只有少数 |

**第三条决定了整套设计**：为"逻辑上存在"的环境持续保留全额物理资源是纯粹的浪费。它的全部机制——暂停恢复、内存回收、快照共享、写时复制分叉——都在回答同一个问题：**怎么让"存在但不活跃"的环境接近零成本。**

这也顺带说明了它为什么不能直接照搬到在线沙箱服务：**在线服务的环境活跃率高得多，能省的空间小得多。**

## 三、先澄清一个概念：硬件隔离就是 CPU 虚拟化

这是很容易被讲混的一处。**"microVM 是硬件隔离"与"microVM 用了 CPU 虚拟化"不是两件事，是同一句话的因和果。**

这里的"硬件"专指 CPU 芯片内的虚拟化电路，**不存在第二套独立的隔离硬件**。"硬件隔离"、"CPU 虚拟化扩展"、"`/dev/kvm` 背后的东西"——三个说法指的是同一个对象。

"硬件隔离"真正对比的是**软件隔离**，分界线只有一条：**越界时拦住你的那一下，是电路做的还是代码做的。**

|  | 越界时拦你的是 | 失效条件 |
|---|---|---|
| 容器 | 内核里 namespace / cgroup 的**代码** | 那段内核代码有漏洞即被穿透 |
| microVM | CPU 里的虚拟化**电路** | 需要 CPU 级别的漏洞 |

## 四、快照为什么可行：状态是封闭的

[第二篇](/posts/sandbox-page-fault/)讲过快照机制本身，这里补的是**前提**——为什么 microVM 能做可靠快照而容器不能。因果链是：

```text
CPU 强制隔离，guest 碰不到宿主的任何东西
        ↓
guest 的一切状态只能落在 VMM 分配的那块内存 + 那组寄存器里
        ↓
状态是「封闭」的——边界之内即全部，边界之外没有属于它的东西
        ↓
可以完整枚举 → 快照能保证「存全了」
```

一个 microVM 在任意时刻的全部状态只有三样：**guest 内存**（宿主上一块连续内存，直接导出）、**vCPU 寄存器**（读出来即可）、**虚拟设备状态**（VMM 自己就是设备的实现者，本就掌握）。**没有第四样，而且这是被 CPU 硬性保证的上限**——guest 没有能力在别处留下状态，因为它碰不到别处。

对比容器的检查点方案，差别不在实现质量，而在面对的状态形态：

|  | 做的事 | 后果 |
|---|---|---|
| microVM 快照 | **不理解地复制**——把 4GB 内存原样写成 4GB 文件，一个字节都不解析 | 简单、可靠，guest 里跑什么都支持 |
| 容器检查点 | **理解之后重建**——每遇到一个文件描述符都要判定类型（普通文件 / socket / 管道 / 事件通知…），分别记录、分别重建 | 支持范围 = 已实现的类型清单；遇到没支持的类型直接失败 |

**容器的状态一半在自己家、一半在宿主内核家**：文件描述符表、已建立的 TCP 连接（对端还在那头等着）、进程号、各命名空间内的对象、挂载表、cgroup 状态——散落在宿主内核的各个子系统里。

**关键困难不在于"多"，而在于"你不知道有没有第七样"**——内核新增一个特性就可能多出一类状态，而往往要到出问题才知道。**"理解之后重建"的代价是：你的理解力就是你的支持范围上限。**

## 五、两套 ring：guest 的系统调用宿主看不见

microVM 场景下有一条关键事实值得单独点出：**特权级这套档位，在 guest 里有独立的一套，两套并存、互相嵌套。**

```text
宿主世界：
  宿主 ring 0 = 宿主内核
  宿主 ring 3 = Firecracker 进程（它自己只是个普通用户态进程，无特权）

  ┌── 进入 guest 模式 ────────────────────┐
  ↓                                      ↑
guest 世界：                              │
  guest ring 0 = guest 内核（传入的那个内核镜像）
  guest ring 3 = guest 里的 python / bash │
  ↓                                      │
  └── guest 内核要碰硬件 → 陷出 ──────────┘
```

|  | guest 里进程发系统调用之后 | 宿主内核看得见吗 |
|---|---|---|
| 普通容器 | 直接进宿主内核 | ✅ 就是它处理的 |
| gVisor | 被拦截层拦下，交给用户态内核处理 | ✅ 拦截层正是为此而设 |
| microVM | **guest 自己的内核处理掉了**，全程在 guest 世界内部 | ❌ **完全看不见** |

**拦截点的位置根本不同，这是 microVM 性能可接受的原因之一。** gVisor 拦在**系统调用**这一层——guest 里每次读写文件都要陷出；microVM 拦在**硬件**这一层——只有 guest 内核真要碰网卡或磁盘时才陷出。guest 里几百万次文件操作，宿主可能一次都不被惊动。

最快的判别法：**guest 里 `uname -r` 与宿主不同即为独立内核**；容器里两者必然相同，看不到宿主进程只是命名空间遮蔽，内核仍是同一个。

## 六、OverlayBD：把 overlay 从文件层下沉到块层

这一节补的正是[第八篇](/posts/sandbox-image-layering/)那个明确的缺口：**OCI 镜像是文件层分层，Firecracker 要的是一整块块设备，两边对不上。**

先说明出处：**OverlayBD 不是这个平台自研的，而是 containerd 的子项目**，源自阿里的 DADI；这个平台是使用方。

核心变换是**叠加的单位从"文件"换成"扇区"**：

|  | 一层里装的是 | 叠出来的产物 | 能否随机读 |
|---|---|---|---|
| overlayfs | 文件（相对下层的文件差异） | **一个目录** | 层本身是归档包，❌ 不可定位 |
| **overlaybd** | **块区间的差异** | **一块块设备** | ✅ 可直接定位到扇区 |

**overlay 的语义完全没变**——依然是上层盖下层、从上往下找、找到第一个有它的层即答案；变的只是查找的键，从"文件名"变成"扇区号"。

为什么必须换？因为**容器要的是目录，虚拟机要的是硬盘**：

```text
容器启动    = 切换到合并后的目录当根   → overlayfs 给出的目录正好可用
microVM 启动 = 需要一块块设备当硬盘插入 → 目录无法插进虚拟机当硬盘

对象存储里的 N 个 overlaybd 层
      ↓ 用户态进程合并成一个视图
      ↓ 暴露成设备节点
  一块普通块设备
      ↓
  直接作为 Firecracker 的根盘挂入 ✅
```

**Firecracker 从头到尾以为自己拿到的是一块普通硬盘**，完全不知道背后是分层的、是远端的、是按需拉取的。而因为层格式换掉了归档包，"读到哪个扇区拉哪一段"才成为可能——**懒加载能力是换到块层的副产品**。

这个改动让**约束的性质变了**：

|  | 约束是什么 | 能否持续优化 |
|---|---|---|
| 传统：整镜像下载解压落盘 | **本地磁盘容量**——决定这台机器能跑哪些镜像 | ❌ 硬上限，只能换更大的盘 |
| 按需拉取，本地盘只作缓存 | **拉取带宽 / 缓存命中率**——只决定快慢 | ✅ 加带宽、扩缓存、调预取都能改善 |

**磁盘不再决定"能不能跑"，只决定"快不快"。** 收益最大的场景是**镜像大 + 单次任务短**——一个 8GB 镜像跑一条命令可能只读了几百 MB，传统方式为"可能会用到"付了全款。而 Agentic RL 恰好是这个形状。

## 七、内存回收与超卖：可压缩与不可压缩的实例

先说一个前置约束：**宿主不能直接抢 guest 的内存，因为它不知道哪些页正在使用**——只有 guest 自己的内核知道。所以必须让 guest 主动交出，这需要两个组件分工：

| 组件 | 职责 | 机制 |
|---|---|---|
| **访问监测** | **找出哪些页是冷的** | 内核功能，采样式观察页访问频率，回收长期未访问的页（主要是命令跑完后再无用处的缓存） |
| **气球驱动** | **把腾出来的还给宿主** | guest 内一个"假装占内存"的驱动：宿主要求回收 N 字节 → 气球向 guest 内核申请这么多 → 拿到后告知宿主"这些页 guest 不会再碰" → 宿主收回另作他用 |

**气球的巧妙之处在于把"牺牲哪些页"的决策权留在 guest 内核手里**——它最清楚哪些可以丢弃，宿主只需要说一个数字。这是"宿主无法安全判断 guest 内存用途"这个约束下唯一可行的形态。

**但真正在使用的匿名内存（进程堆栈、变量）一页都省不掉**，能省的只有缓存那部分——这直接决定了内存超卖的天花板。

于是超卖比出现了一个近三倍的差距，而它正好是[第六篇](/posts/sandbox-resource-model/)那组对立的实例：

|  | 为什么能超卖 | 要做什么 | 超过头的后果 |
|---|---|---|---|
| **CPU**（约 27.9×） | vCPU 只是宿主上的普通线程，guest 等模型输出时线程阻塞，**不消耗任何 CPU** | **什么都不用做**，宿主调度器天然把 CPU 给别人 | 变慢、排队（**可压缩**） |
| **内存**（约 9.6×） | 只有缓存那部分可回收 | 要跑扫描（有开销）+ 气球充气（guest 内感到内存压力）+ 快照页共享 | **OOM，直接杀掉整台 VM**（**不可压缩**） |

**27.9 倍的 CPU 超卖没有任何魔法**——vCPU 是宿主上一个普通线程，它的主循环是"进入 guest 模式执行 → 卡住直到陷出 → 处理 → 回到循环"，而绝大多数线程正阻塞着，不占 CPU。

## 八、这些数据可信吗

案例引用要标明底数，否则容易把厂商口径当成客观结论：

| 数据 | 性质 |
|---|---|
| 49ms 启动 / 133ms 快照 | **可信度相对高**——量级由机制决定（懒加载的快照恢复只建映射不读数据），与 Firecracker 公开的量级相符 |
| CPU 27.9× / 内存 9.6× 超卖比 | **厂商自述的生产观测**，非第三方复现；但机制上可解释（见上一节） |
| 成本降低百分之八九十 | **需特别注意口径**：对比方式是"自身超卖后的实际用量"对"他方按申请量计费"，**这个口径天然对自身有利**。原文亦附了免责说明 |
| 单节点 400 环境 / 集群 3 万环境 | 厂商自述部署规模，未见第三方验证 |

这一栏值得单列，因为**案例分析最容易出的问题就是把营销数字当机制结论**。机制能解释的（启动量级、超卖为什么 CPU 远高于内存）可以信；口径可选的（成本对比）必须看清怎么算的。
