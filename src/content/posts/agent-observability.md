> 本文是「Agent 工程」系列第 11 篇。[评估那篇](/posts/agent-evaluation/)讲的是**指标**，这一篇讲**追踪**。二者回答的问题不同：

|  | 回答什么 | 形态 |
|-|-|-|
| **指标** | 整体健康吗？有没有退化？ | 聚合数字，跨很多次运行 |
| **追踪** | **这一次**到底发生了什么？慢在哪、错在哪？ | 单次运行的完整过程 |

调试一次具体故障时指标帮不上忙——它只告诉你"打转率涨到 9%"，不告诉你"第 47 号会话为什么打转"。

## 一、为什么日志不够

用户投诉"跑了 3 分钟才回复且答错了"，手上通常是一堆日志：每行只有时间戳与一句话，**耗时要自己拿减法算**、**哪几行属于同一次工具调用只能猜**、**子 agent 的日志与主线混在一起**、**并发执行时日志交错**。

日志是"一串离散事件"，没有结构；而 agent 的一次运行是有结构的：

```text
invoke_agent                                    180s   ← 顶层，整个 3 分钟
├─ chat (模型调用)                                6s
├─ execute_tool  grep                             1s
├─ chat                                           6s
├─ execute_tool  run_tests                      102s   ← 慢在这里
├─ chat                                           7s
├─ execute_tool  spawn_subagent                  52s
│   └─ invoke_agent  (子 agent 自己的树)          52s
│       ├─ chat                                   8s
│       ├─ execute_tool  read_file                1s
│       └─ chat                                  43s
└─ chat                                           6s
```

问题于是一目了然：慢在哪一眼可见；子 agent 是独立子树、不与主线混杂；并发的时间区间重叠，画出来是并排而不是交错。

**这棵树的形状是前面几篇结构的投影**：外层循环 → 每轮的模型调用与工具执行 → 子 agent 内部又是一整棵子树。它与[子 agent 那条链树](/posts/agent-checkpoint-storage/)是同一结构的两个视角——**链树是状态视角（对话历史归谁），这棵树是过程视角（哪段执行发生在谁内部）**。

还有一个实现上的关键事实：**没有人"组合"这些记录，树是后端重建出来的。** 运行时每一段各自独立上报、各自带着父指针，顺序甚至可能乱；后端按运行编号取出全部记录，再按父指针拼成树。**顶层那个节点只是根，它不负责收集别人。** 因此"树"只在查询时存在，运行时只有一堆扁平的、带指针的记录——**与 [checkpoint 那张只追加的表](/posts/agent-checkpoint-storage/)完全同一手法。**

## 二、与 checkpoint 的分工

|  | 记录什么 | 用途 |
|-|-|-|
| **checkpoint** | 状态是什么（第 5 步结束时历史长什么样） | 恢复、重放 |
| **追踪** | 过程发生了什么（那一步花了 12 秒、9 秒卡在某工具、哪步报错） | 调试 |

**两者互补才完整**：追踪告诉你"哪一步出了问题"，checkpoint 让你**从那一步分叉重放**去复现。**非确定性使"照着日志复现"不可行，但"从那个状态重新开始"可行**——这是 checkpoint 链在本系列里的第三个用途（恢复、评估语料、调试复现）。

## 三、什么时候不需要上 OTel

**这一节放在工具选型之前，因为顺序反了会付出真实成本。**

先把术语理顺：一段有开始有结束的操作记录叫 **span**，它比一行日志多两样东西——**自带持续时间**、**带结构化属性**；一次完整运行中所有 span 组成的**树**叫 trace；**OpenTelemetry** 是一个开放标准，规定这些数据长什么样并提供各语言 SDK。要强调的是：**"OTel span"不是另一种东西，就是"按这套标准格式填字段的 span"**——类比"网络请求"是概念、"HTTP 请求"是它的一套具体规范。

而 **SDK 只负责产生与导出，不负责存储与查询**，必须另外部署一个后端来接收。**这是最常见的误解：装了 SDK 还不够。** 很多人装完发现"什么也没有"，就是缺了这一环。

那么什么时候不需要？**如果你的调用是单进程、同步、层次浅的，它不带来任何优势**——日志加一张表更划算，实现只需几十行：

```sql
CREATE TABLE spans (trace_id, span_id, parent_id, name, start, duration, attrs);
```

追踪本质上就是"结构化日志 + 父指针 + 耗时字段 + 配套工具"，没有魔法。**判断标准只有一条：你的调用有没有异步、并发、跨进程。** 没有则自建足够；有则自己实现上下文传播的成本会超过接一个 SDK。

## 四、SDK 唯一真正解决的问题

计时、生成编号、拼树，自己写都是几十行的事。**难的只有一件：让每段代码都能拿到"当前这一段是谁"。**

```python
current_span = None                      # 全局变量

await asyncio.gather(execute(A), execute(B), execute(C))
# 三个协程交错执行：A 把 current_span 设成自己，切到 B，
# B 又覆盖成自己，切回 A —— A 读到的「当前」是 B 的，父子关系全错
```

于是只能改成显式传参，而**这个参数要穿透所有调用层**，每个函数都多一个与业务无关的形参。跨进程更麻烦：发出前自己把上下文写进请求头、对端自己取出、格式自己定，然后在对端进程里把上面那套传参再重复一遍。

SDK 用的是语言层的上下文机制，**协程切换时会自动切换这份上下文**，所以并发下不会串，函数签名也保持干净；跨进程那段也有标准的注入与提取，格式统一因而能与框架自己发出的记录拼进同一棵树。

**但要看清它保证的是什么：它保证"树的结构正确"，不保证"树的内容完整"。** 手写最典型的失败不是"少记了一段"，而是"记了但挂错了"——并发时串到别的协程、跨进程后成了孤儿。**这两种都不报错**，你只会在查问题时看到一棵形状诡异的树，还以为代码真的那么跑。至于"在哪开一段、记什么属性"，任何方案都要你自己决定，SDK 不管。

| SDK 替你做 | 仍然要你决定 |
|-|-|
| 创建、结束、自动计时；编号生成；**上下文传播**（同步、异步、线程池、跨进程）；采样；按标准协议导出 | 在哪些位置开一段（业务决策）；记哪些属性；**部署一个后端来接收**；采样率与保留时长 |

## 五、无状态服务为什么反而更需要它

"我的 agent 是个无状态服务，为什么还要关心这个"——这里有个正交关系：**无状态说的是请求之间不共享状态，追踪关心的是一次请求内部发生了什么。** 服务无状态不代表一次请求内部简单：

| 服务类型 | 一次请求内部 | 需要追踪吗 |
|-|-|-|
| 普通无状态增删改查 | 查一次库，20 毫秒，两三行日志 | 不需要 |
| agent 服务 | 3 分钟，十余次模型调用，数十次工具执行，若干并发，还有跨进程调用工具沙箱 | **一次请求内部就是几十个操作** |

**而且无状态反而让问题更糟**：无状态服务的常态是一个进程同时处理很多请求，**多个会话的日志天然交错**，连"哪几行属于同一次运行"都分不出来。反倒是有状态、单会话独占进程的服务更好办——那个进程的日志就是那次会话的。**正因为无状态、多请求共用进程，才必须有个编号把它们串起来。**

## 六、落地顺序：最小需求不是"要不要上 OTel"

而是：**能不能把某一次运行的全部记录，从混在一起的日志里完整取出。**

```text
① 给每次运行一个 run_id，所有日志都带上它
     → 几乎零成本，从「200 行交错日志」变成「按 run_id 过滤出这 40 行」
     → 这一步就能解决约八成的痛

② 手写几个关键计时点，写入一张表
     → 先看清哪几段慢

③ 确有必要时再上 SDK

④ 最后才考虑托管后端（自建够用就先自建）
```

**什么时候算"确有必要"？一个具体信号：当你开始需要问"这一步是在哪一次运行的哪一轮里发生的"，而现有日志答不上来的时候。** 在那之前，一个运行编号加几个计时字段就够了。

**追踪编号就是运行编号的标准化版本，span 树是它的加强版**（多了父子关系与耗时）——你是先要那个编号，之后才谈得上要不要树。**在真正被断树问题困扰之前就引入 SDK，会付了接入成本却感受不到收益。**

## 七、语义约定与"要不要记完整提示词"

标准分三层，逐层变具体：**核心规范**（所有记录都有的编号、名字、起止、属性，与领域无关）→ **语义约定**（某领域该用什么名字与属性）→ **面向生成式 AI 的语义约定**。第三层具体规定了节点名字（前面那棵树里的名字不是示意，就是规范里的标准名字）、必需的延迟与消耗量指标、模型名与输入输出量等属性，以及**显式开启之后**才记录的完整提示词、输出、工具调用与结果。

两点提醒：

**稳定性。** 前两层已稳定多年，**面向生成式 AI 的这一层属性名带开发中稳定性标记——可能在不升主版本号的情况下变更**。现在接入没问题（主流厂商与框架已支持），但**别把属性名硬编码到很多地方**。

**要不要记完整提示词，是个真实取舍**，这也是规范把它设为需显式开启的原因。体积上：每一段都带完整提示词，而提示词含全部历史，存储量是平方级的（与 [checkpoint 全量快照](/posts/agent-checkpoint-storage/)同一问题）。隐私上：用户数据与凭据都可能在里面，全量落进可观测系统等于扩大泄露面（见[上上篇](/posts/agent-prompt-injection/)）。**常见折中：默认只记结构（模型、消耗量、耗时、工具名），完整内容按采样或仅对失败记录**——失败的那些才是要调试的。
