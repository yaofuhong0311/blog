## 一、gVisor：两种模式，只有一种算"中间件"

沙箱进程发起的任意系统调用，默认路径是直接流入宿主内核，**不存在天然的拦截点**。gVisor 的做法是在这条路径上人为插入拦截（默认基于信号机制，也可选硬件虚拟化），拦截之后交给 Sentry——一个用户态实现的"内核"，承担同样的系统调用处理职责，只是特权级别不同。接下来按配置分成两条路：

| 模式 | 机制 |
|-|-|
| **netstack（默认）** | Sentry 自己实现了一整套 TCP/IP 协议栈。建立连接、收发数据**不产生任何宿主机的网络系统调用**，连接对象纯粹是用户态内存里的模拟。它与宿主内核唯一的接触点是：启动器摘掉容器网卡的 IP，开一个裸 socket 绑上去，把文件描述符交给 Sentry；出包时协议栈在用户态把以太网、IP、TCP 各层头部拼好，一次性整包发出——**宿主内核只提供一根管子**。 |
| **hostinet** | Sentry 不跑自研协议栈，直接发起真实的宿主机网络系统调用。快，但比默认模式多暴露约十几个真实网络调用给过滤面，隔离变弱。 |

两种模式的本质区别值得单独点出来：**netstack 没有"下家"**——它是完全的替身，不存在被转发到的真实网络栈；**hostinet 才符合中间件的语义**——拦截之后转发给真实实现、再取回结果。把 netstack 叫做"一层中间件"是不准确的。

## 二、microVM：hypervisor 层字面意义上的零过滤

Firecracker 的路径是：guest 内是半虚拟化网卡，走共享内存的环形队列协议（而不是模拟真实网卡的寄存器时序）；宿主侧对接一个虚拟以太网接口，一端接内核网络栈，另一端是用户态程序持有的文件描述符。

关键在于**Firecracker 不建这个接口、不配 IP、不做桥接和地址转换**——运维预先建好，把设备名通过 API 传进去。官方文档的原话是：它不执行任何网络流量过滤，guest 的所有出站流量都应视为不可信，应当在宿主机层面过滤。网络 I/O 边界上它只做限速，不做安全检查。

Kata 的情况稍复杂：网络插件只理解 Pod 网络命名空间里的虚拟网卡对，不理解"VM"这个概念。默认方案是在同一个命名空间内建一个虚拟接口给 VM 用，再装两条双向镜像规则把流量搬过去。

**共性是：hypervisor 层都不做防火墙**，只解决"包如何从普通的 Linux 网络对象搬进 guest 的虚拟网卡"这个物理搬运问题，过滤策略完全交由宿主机承担。这与容器路径（宿主侧的包过滤）在"谁执行过滤"上没有本质区别，区别仅在于网络对象从一种虚拟网卡换成了另一种。

顺带把发包这条链完整走一遍，它正好对应虚拟化里 KVM 与 VMM 的分工：① guest 内核把待发数据写入与 VMM 共享的队列（这是一次对"故意没接真实硬件"的虚拟地址的写操作）；② 这次写触发陷出，KVM 捕获——**KVM 在这一步只做"发现陷出、交还控制权"，不解读内容、不做转发**；③ 控制权回到 VMM，VMM 自己读出队列里的包数据，调用普通系统调用写进那个虚拟接口；④ 宿主内核接手，按普通流程转发。"KVM 抓陷出"和"VMM 真正操作宿主机资源"是完全分开的两步。

## 三、为什么"按域名放行"是协议层面的硬限制

K8s 原生的网络策略是纯粹的三四层原语——选择器、地址段、端口，**字段体系里根本没有域名这个维度**。这是协议层面的硬限制，不是配置缺失。

根源在于：域名系统负责把域名翻译成 IP，**翻译完成后，真正发出的网络包上只写 IP，域名不再随包传递**。域名信息只在两个窗口短暂可见——查询那一下，以及 TLS 握手第一条消息里的服务器名称字段那一下。

而且 IPv4 地址稀缺，现代服务器软件与 CDN 普遍让同一小撮 IP 同时承载大量互不相关的域名，彼此的所有者互不相识。服务器靠请求里携带的名称字段而不是 IP 本身来区分该返回哪个网站——这正是那个字段存在的必要性来源。

于是生产环境有两条外挂路径，通常搭配使用：

- **路径中的代理**：读 HTTP 隧道请求里的明文主机名；或者透明代理在 TLS 握手的第一条消息里读明文的服务器名称字段——不解密，只在握手最初那一瞬间看一眼域名，之后原样转发剩余字节。
- **感知域名系统的策略引擎**：坐在查询路径上，把真实解析出的 IP 连同存活时间绑定到域名，做成短命白名单（成熟实现还会附带一个宽限期，防止长连接被存活时间到期误杀）。

这里有两个需要澄清的点。

**"按域名放行"做不到，不代表"按 IP 放行"也做不到。** 地址段字段本来就是为 IP 白名单设计的，锁定单个公网 IP 加端口完全可行。做不到的只是"填一个域名进去"。**但把域名解析出来的 IP 硬编码进去是个陷阱**：CDN 或多副本场景下，同一域名会随地理位置和负载返回不同 IP，写死的那一个很快就不再匹配，合法请求会被当成不在白名单而拒掉——这与"缓存了 Pod IP 之后 Pod 重启换了 IP"是同一类错误：**把一个本质会变的值当成固定值固化下来**。这也正是感知域名系统的策略引擎存在的理由，它维护的规则跟随每次真实解析刷新。

**那个策略引擎不是旁路监听者，而是必经节点——这决定了它为什么没有竞态。** "偷听"这个词容易让人以为引擎在旁边被动观察、与沙箱同时收到应答，那样确实会出现"沙箱已拿到 IP 发起连接、引擎规则还没写完"的抢跑窗口。实际部署是引擎**卡在沙箱与真实域名服务器之间**：查询必须经它转发，应答也必须经它放行。它的执行顺序是"先把该 IP 的放行规则写进下游规则表，再把应答交给沙箱"——两件事由同一个组件按序完成，沙箱在拿到 IP 之前无从发起连接。

另外要分清两个环节的职责：**域名白名单的判断发生在解析环节，流量的拦截仍然发生在连接环节**，由三四层规则执行，两者通过一张动态维护的 IP 规则表串联。不在白名单的域名，它的查询照常成功返回真实 IP，只是没有任何规则为该 IP 放行，连接在第二个环节被拒。

## 四、两个高优先级陷阱

| 陷阱 | 机制 |
|-|-|
| **重绑定攻击** | 如果"检查"和"真正连接"是两次独立的解析，攻击者控制的域名服务器可以在检查那一刻返回安全 IP 骗过校验，随后把同一域名重新指向内网或云元数据地址用于真正的连接。感知域名系统的引擎因为绑定的是查询时真实解析出的那个 IP，不受这个骗术影响；而"按解析结果做一次性判断"的实现会中招。 |
| **握手加密** | 新的协议扩展会把 TLS 握手的第一条消息本身也加密，服务器名称字段不再明文可见，纯嗅探型代理未来会失效；而隧道式代理因为在 TLS 握手开始之前就拿到了明文主机名，不受影响。 |

## 五、三档对照与决策

| 维度 | 谁执行出站过滤 | 网络路径的隔离强度 |
|-|-|-|
| 容器 | 宿主机的包过滤 + 网络策略 | 弱——网络命名空间本身不隔离策略 |
| gVisor | 同样落回宿主机 | 协议栈搬进用户态 + 全量拦截系统调用，打到宿主内核的攻击面压缩到几个读写操作；防的是"逃到宿主内核"，不是"访问了不该访问的域名" |
| microVM | 完全交由宿主机承担 | 真实独立的 guest 内核 + 虚拟化硬件边界，与裸容器不是一个量级 |

**决策规则：** 在"能否表达域名级出口白名单"这件事上，三种引擎均无内置能力，均收敛到宿主机层执行——这不是引擎的短板，**该能力本就不属于沙箱隔离层的职责范畴**，而属于七层代理或域名感知引擎的职责范畴。因此域名级出口控制的选型与"选哪种沙箱引擎"**正交**：无论选容器、gVisor 还是 microVM，都需要外挂同一层。

最后纠正三个常见误判：

- **"服务器名称字段是在 TCP 三次握手里传的"**——不对。三次握手只交换 IP 和端口，不携带任何域名信息；那个字段出现在 TCP 连接建立**之后**才开始的 TLS 握手的第一条消息里，是两个不同协议层前后接续的独立握手。
- **"netstack 是一种中间件"**——不准确，前面已经说过：它拦截之后没有下家。
- **"microVM 的硬件边界意味着网络也更安全"**——不成立。出站过滤这件事上 microVM 与容器最终都在宿主机层执行，microVM 的边界优势体现在"逃逸"维度，不体现在"域名访问控制"维度。
