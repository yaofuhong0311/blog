> 本文是「Agent Sandbox 工程实践」系列第 1 篇。这个系列不再重复介绍沙箱的基础隔离机制，而是讨论控制面如何把运行时、存储和任务状态组织成可恢复的平台能力。

一次 Agent 任务正在 Sandbox 中执行，Pod 突然消失，但 Workspace 中的文件仍然存在。控制面下一步应该怎么做？

最直接的处理方式是创建一个新 Pod、重新挂载 Workspace，然后继续任务。然而，这个方案隐含了一个未经证明的前提：**旧 Sandbox 消失之后，新环境能够准确恢复旧任务的执行位置，并且不会重复产生外部副作用。**

文件仍然存在，只能证明部分持久化数据没有丢失。内存进程、Shell 会话、网络连接、临时目录，以及某条命令究竟执行到什么位置，可能已经无法恢复。控制面面对的因此不是单纯的 Pod 重建问题，而是一个状态判断问题：

```text
任务是否仍需继续？
运行环境是否仍然存在？
上一个业务动作是否已经完成？
如果重新执行，是否会产生第二次副作用？
```

这些问题不能由一次请求中的局部上下文稳定回答。它们需要一份可持久读取的任务依据，以及一个持续比较任务状态与运行状态的控制循环。

## 一、问题不是 Pod 能否重新创建

Kubernetes 本身能够重新创建工作负载。Deployment、Job 等控制器会观察当前状态，并让实际状态向声明的期望状态靠近。Kubernetes 官方文档将 Controller 定义为持续观察集群状态、在需要时执行或请求变更的控制循环。

但 Kubernetes 能够创建替代 Pod，不代表业务任务能够从原位置继续。这是两个不同层次的问题：

| 层次 | 需要回答的问题 |
|-|-|
| 运行环境 | Pod 是否存在，镜像能否启动，Workspace 能否挂载 |
| 业务任务 | 哪一步已经完成，哪一步可以重试，外部副作用是否已经发生 |

如果任务只是读取文件并运行一组确定性测试，新建 Sandbox 后从步骤起点重新执行通常可行。如果任务正在发消息、提交远程作业、修改数据库或发布版本，重复执行可能产生第二份不可撤销的结果。

因此，运行时的自愈能力只能恢复“可执行环境”，不能自动恢复“业务执行语义”。控制面必须先确定任务状态，再决定是否创建新环境。

## 二、三种状态不能混为一谈

设计 Sandbox 控制面时，至少要区分三类状态。

### 1. 期望状态

期望状态描述系统希望任务最终达到什么结果，例如：

```text
Rollout 仍需执行
当前应位于第 4 个步骤
需要一个绑定指定 Workspace 的 Sandbox
Sandbox 的有效期应延长到某个时间
```

这份状态可以记录在任务、Job、CRD 或数据库中。系统规模较小时，不一定需要单独建立一套 Sandbox 数据库；只要现有任务记录能够保存任务阶段、`sandbox_id`、Workspace 和生命周期信息，它就可以成为对账依据。

### 2. 观测状态

观测状态来自当前真实环境，例如：

```text
Sandbox 是否存在
Pod 是否 Ready
Workspace 是否成功挂载
命令是否仍在运行
TTL 是否接近到期
```

它不是上一次请求结束时留下的推测，而是控制面重新查询运行时、Kubernetes 或动作状态接口得到的结果。

### 3. 业务状态

业务状态解释某个动作对任务意味着什么：

```text
尚未提交
已经提交但结果未知
已经成功
已经失败且允许重试
已经失败且必须终止
```

同一个观测事实可能对应不同业务结论。例如“Sandbox 不存在”既可能意味着任务尚未开始，也可能意味着任务执行成功后环境已经回收，还可能意味着执行过程中异常退出。仅凭运行环境状态无法区分这三种情况。

Kubernetes 对象中的 `spec` 与 `status` 已经体现了期望状态和当前状态的分离。但 Agent Sandbox 还需要增加业务动作这一层，因为外部 Tool 和远程系统并不一定属于 Kubernetes 能够直接观察和恢复的范围。

## 三、Reconcile 负责持续对账

Reconcile 的核心不是按固定顺序执行一条长流程，而是反复完成以下步骤：

1. 读取可靠的任务依据；
2. 查询 Sandbox 与动作的真实状态；
3. 比较期望状态和观测状态；
4. 根据业务状态分类差异；
5. 执行一个范围明确、可以再次检查的动作；
6. 保存结果，等待事件或进入下一轮检查。

![Agent Sandbox 控制面的状态收敛循环](/images/posts/agent-sandbox-reconcile-loop.svg)

请求链式执行与 Reconcile 的差异可以表示为：

```text
请求链式执行
创建 Sandbox → 等待 Ready → 执行命令 → 保存结果
任意一步中断后，调用栈和局部上下文可能同时消失

状态收敛
读取依据 → 查询现状 → 处理一个差异 → 保存结果
进程重启后，可以从同一份依据重新判断
```

这并不意味着每个系统都必须实现 Kubernetes Operator。Reconcile 是一种控制方式，可以运行在定时任务、消息消费者、服务内后台任务或自定义 Controller 中。关键约束是：**每一轮判断都以可重新读取的状态为输入，而不是依赖上一轮仍然存活。**

这种结构也不要求系统最终永远处于静止状态。任务可能正在执行，Sandbox 可能正在创建，TTL 可能持续变化。控制面的目标是让每个变化都能被观察、分类和再次处理，而不是强制系统在单次请求结束前完成全部工作。

## 四、Sandbox 消失不等于任务可以重做

当任务记录显示“仍需执行”，但对应 Sandbox 已经不存在时，控制面只能得出一个结论：**期望状态与观测状态不一致。**

它不能立即得出“创建新 Sandbox 并重新执行”的结论。原因在于，新环境能够恢复的状态非常有限：

| 可能保留 | 通常已经丢失 |
|-|-|
| Workspace 文件和持久化产物 | 进程内存与文件描述符 |
| 已经写入外部存储的任务记录 | Shell 会话与子进程树 |
| 已确认完成的动作结果 | 临时目录和未刷新的缓冲区 |
| 可重新获取的固定输入 | 网络连接与远程事务上下文 |

新 Pod 获得的是“带有旧文件的新执行环境”，并不是旧进程原地恢复。除非使用了能够保存进程现场的运行时快照，否则控制面只能从某个业务步骤的起点重新执行。

即使运行时支持 Snapshot，也不能直接替代任务 Checkpoint。运行时 Snapshot 保存的是 RootFS、内存、CPU 或设备状态；任务 Checkpoint 保存的是步骤编号、动作状态和业务结果。前者降低环境恢复成本，后者决定恢复后应该做什么。两者解决的问题不同。

关于 Kubernetes 声明式控制的基础机制，可以继续阅读[《K8s 的声明式世界观》](/posts/sandbox-declarative-k8s/)；关于执行生命周期由谁拥有，可以参考[《Session 执行控制与 Tool 恢复》](/posts/agentscope-runtime-ownership/)。

## 五、恢复决策必须建立在业务语义上

恢复流程首先要确认原 Sandbox 是否存在；如果已经不存在，就必须继续判断上一个动作的结果。

![Sandbox 消失后的恢复决策](/images/posts/agent-sandbox-recovery-decision.svg)

可以安全重新执行的任务通常具有以下特征：

- 只读查询；
- 使用固定输入重新运行测试；
- 可重复下载且结果能够覆盖；
- 动作具有强幂等键，同键请求只会得到同一业务结果；
- 上一步结果可以通过独立接口查询。

不能直接重新执行的任务包括：

- 发送消息或通知；
- 扣费与资源购买；
- 提交无法按业务键去重的远程作业；
- 修改远程数据库；
- 发布制品或切换生产版本。

这些动作的共同风险不是“可能失败”，而是**上一次可能已经成功，但成功结果没有返回**。如果控制面在无法确认结果时重新执行，就可能产生两次成功。

因此，恢复策略至少需要三种终态：

```text
可恢复：从明确步骤重新执行
失败：确认无法继续或不允许重试
待确认：结果存在歧义，需要查询外部系统或人工判断
```

“待确认”不是异常设计，而是对分布式系统不确定性的显式表达。与其把未知状态强行归类为失败并自动重试，不如保留现场、动作标识和原因，让上层任务系统做出符合业务语义的决定。

## 六、当前工程能够确认的能力边界

在我当前维护的一套 Sandbox 控制面中，已经具备以下基础能力：

- 创建、查询、续期、诊断和删除 Sandbox；
- 在 Sandbox 中同步或异步执行命令；
- 通过 Workspace 持久化用户文件和任务产物；
- 为创建和异步命令提供请求级幂等；
- 查询异步命令的运行状态和结果；
- 在客户端取消创建时清理可能产生的孤儿 Sandbox。

这些能力解决了单个 Sandbox 和单个动作的生命周期问题，但不能自动推导整个 Agent 任务应该从哪一步继续。当前实现也不能仅凭 Sandbox 消失这一事实，安全地重建环境并恢复任意 Rollout。

任务级恢复仍然需要上层保存：

```text
当前步骤
动作标识
幂等键
已确认结果
Workspace 位置
恢复策略
```

这里还需要明确证据边界：控制面能够描述镜像、资源、环境变量、Workspace 和命令，却不代表它能够从这些参数判断底层使用普通容器、gVisor 还是 MicroVM。运行时类型需要由实际 Pod、RuntimeClass 和节点配置确认，不能从抽象创建接口推断。

## 七、如果由我设计当前控制面

在这些事实和边界之上，我会先选择一套范围较小、能够验证恢复语义的控制面，而不是立即建设完整的 Sandbox 平台数据库和通用恢复框架。

| 决策 | 当前选择 | 原因 | 需要升级的条件 |
|-|-|-|-|
| 任务依据 | 复用现有 Rollout、Job 或任务记录 | 现阶段缺少的是恢复语义，不是另一份状态副本 | 需要跨集群查询、独立生命周期或复杂租户关系 |
| 恢复职责 | 控制面只分类为可恢复、失败或待确认 | 是否重做取决于业务副作用，底层无法统一判断 | 上层任务都具备稳定的动作协议和强幂等保证 |
| 幂等记录 | 单副本阶段可以使用进程内记录，但明确限制部署形态 | 先验证接口语义，避免过早引入共享组件 | 服务需要多副本或要求跨重启保持同键结果 |
| 状态保存 | Workspace、动作记录、任务 Checkpoint 分层保存 | 三者的恢复粒度和权威持有者不同 | 不合并；只根据规模替换各层的存储实现 |

### 1. 暂不新增独立 Sandbox 数据库

如果现有任务记录已经能够保存 `sandbox_id`、Workspace、当前步骤和 TTL，我会先把它作为期望状态的权威来源。再增加一张 Sandbox 表，会立即引入“双份状态以谁为准”的问题，却不会自动补齐动作结果和恢复策略。

只有当 Sandbox 开始脱离单个任务独立存在，或者系统需要管理多集群、长生命周期、租户关系和跨任务复用时，独立状态模型才值得引入。届时它解决的是新的查询和生命周期需求，而不是为了形式上拥有一套“控制面数据库”。

### 2. 不实现通用的自动重建

我不会让底层在发现 Sandbox 消失后直接创建新实例并重放最后一条命令。底层能够确认的是环境状态，不能确认发消息、扣费、提交远程任务等动作是否已经产生副作用。

更稳妥的接口是输出一项恢复判断及其原因：

```text
RECOVERABLE  已确认可以从步骤起点重做
FAILED       已确认无法继续或策略禁止重试
UNCERTAIN    上次结果无法确认，需要查询或人工处理
```

真正执行哪一步，由掌握任务图和业务语义的上层决定。这样会减少一部分“全自动恢复”，但避免控制面以基础设施自愈的名义重复业务动作。

### 3. 多副本之前先解决共享幂等

进程内幂等记录适合验证接口顺序和并发占位，但它同时规定了系统上限：服务重启后记录消失，请求落到另一副本也无法识别同一个键。

因此，在扩展为多副本之前，我会先把以下映射迁移到支持原子占位的共享存储：

```text
idempotency_key
→ processing state
→ sandbox_id / action_id
→ terminal result
```

这里的顺序比存储产品更重要：必须先占位，再执行外部动作，最后保存结果。Redis、数据库或其他存储只是实现选择，不能修复错误的写入顺序。

### 4. 最小恢复记录只保存可解释状态

第一版任务 Checkpoint 不需要复制完整运行时状态。我会先保存一组能够解释“下一步为什么这样做”的字段：

```text
task_id
current_step
sandbox_id
action_id
idempotency_key
action_status
recovery_reason
updated_at
```

这组记录不能恢复进程内存，但能够支持审计、结果查询和步骤级重试。运行时 Snapshot 可以在后续用于降低冷启动时间，却不应该成为任务状态的唯一依据。

这套方案的取舍很明确：它优先保证恢复决策可解释、外部动作不重复，然后才增加自动化程度。若未来所有动作都提供强幂等键、可查询结果和稳定 Checkpoint，再扩大自动恢复范围会更安全。

## 八、设计检查清单

为 Sandbox 生命周期增加恢复逻辑前，可以先检查以下问题：

- 是否存在可持久读取的任务依据？
- 期望状态、观测状态和业务状态是否分开记录？
- Sandbox 消失后，能够确认上一个动作的结果吗？
- 重试依据是业务幂等，还是仅仅因为接口返回失败？
- Workspace 保存了哪些数据，又没有保存哪些执行现场？
- 控制面重启后，能否重新判断当前状态？
- 多副本是否读取同一份任务和幂等记录？
- 无法确认动作结果时，是否有待确认或人工介入状态？
- 创建新 Sandbox 后，从哪个明确步骤重新执行？
- 是否记录了恢复原因，便于后续审计和排障？

## 九、结论

Agent Sandbox 控制面的价值不只是创建和删除运行环境。更重要的职责是持续回答：任务希望达到什么状态、运行环境现在处于什么状态，以及两者不一致时可以采取什么动作。

Reconcile 将一次容易中断的长流程改造成可重复判断的控制循环，但它只负责发现和分类差异。Sandbox 消失后能否恢复，仍取决于业务动作是否可查询、可幂等执行，以及任务是否保存了明确的 Checkpoint。

因此，可靠的恢复顺序不是“发现 Pod 消失后立即重建”，而是：

```text
重新读取任务依据
→ 查询 Sandbox 与动作状态
→ 判断结果是否存在歧义
→ 根据业务幂等性选择继续、重试、失败或待确认
→ 需要时再创建新的执行环境
```
