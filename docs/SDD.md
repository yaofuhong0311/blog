# SDD — 个人博客

## 目标
个人博客站点，承载三类内容：自制小工具展示、学习笔记、AI Coding 经验分享。

## 技术选型
- **模板**：Fuwari（Astro + Tailwind + Svelte），clone 自 saicaca/fuwari，保留上游结构便于后续手动同步更新。
- **部署**：Cloudflare Pages，连 GitHub 仓库自动构建；先用 `*.pages.dev`，自定义域名申请下来后绑定。
- **包管理**：pnpm。

## 结构约定
- 文章：`src/content/posts/`，Markdown，学习笔记 / AI Coding 经验用分类（category）区分，不另设页面。
- 工具展示页：`src/pages/tools.astro`，数据来自 `src/data/tools.ts`（新增工具 = 加一条配置 + 可选截图放 `public/images/tools/`）。工具本体不在站内运行，只做介绍 + GitHub/下载链接。
- 站点配置集中在 `src/config.ts`（标题、语言 zh_CN、导航、个人资料）。

## 内容系列边界
- “沙箱底层机制”解释隔离、存储、网络、调度和运行时原理。
- “Agent Sandbox 工程实践”解释控制面如何组合状态收敛、故障恢复、隔离选型与冷启动优化。
- 两个系列通过站内链接互补，不在新专题中重复展开已有基础原理。

## 内容写作约定
- 机制说明与源码事实之后，应给出有证据支撑的个人工程判断。
- 工程判断至少说明当前选择、选择原因、承担的代价和需要调整方案的触发条件。
- 工具页不强制使用统一标题；已有“为什么做”“设计取舍”时保留自然结构，只补缺失的适用边界。
- 区分事实、推断和个人选择，不用主观措辞替代证据。
- 每篇文章只承载一个中心判断；标题、摘要和开头应使用同一问题表达，避免读者进入正文后重新识别主题。
- 开头优先给出问题、结论和阅读收益，不以系列说明、调研过程或术语背景作为主要首屏内容。
- 普通文章的默认正文目标为 1500～2200 个中文字符，主体二级章节不超过 4 个；源码调研可保留额外证据，但详细调用链、代码片段和边界枚举应放入可展开的“实现依据”。
- 图表只保留直接帮助理解中心判断的内容；已有专题能够完整解释的机制通过站内链接承接，不在新文章中重复展开。
- 文章按内容性质采用不同论证路径：源码调研回答“源码如何证明机制”，工程实践回答“为什么选择当前方案”，学习笔记回答“概念如何共同解释问题”，工具介绍回答“解决什么问题以及适用边界”。
- “快速阅读”只列出能够独立成立并在正文中得到论证的判断，不复述章节目录；主论证不得依赖展开折叠内容才能成立。
- 允许删除重复、偏题、过程性和不能支撑中心判断的内容；`<details>` 只承接源码、配置、完整表格和边界枚举。

## 内容信息架构
- 本节分类约定取代“结构约定”中以“学习笔记 / AI Coding”区分文章的旧说明。
- 系列用于组织有顺序的连续阅读，分类用于表达单篇文章的内容性质，两者不重复承担导航职责。
- 分类固定为 Agent 工程、沙箱系统、源码调研、工程实践、AI Coding、随笔；新增分类前先确认现有分类无法准确承载。
- 工具与 Demo 使用独立工具页，不为工具条目重复创建文章分类。
- 侧栏按专业主线排序分类，不按名称字典序排序；六个分类全部展开，保持入口可见。
- 文章若对应本人已公开的 GitHub 工程，应在开头提供 GitHub 源码与站内工具说明入口；纯学习笔记和第三方源码调研不强制关联仓库。

## 明确不做（要了再加）
- 评论系统（候选方案 giscus，零后端）
- 工具网页版站内运行、访问统计、英文版
